# Format Kit

### Overview

The format kit is a pure TypeScript library in `src/lib/format-kit/` that describes a league or tournament format as **data**: a versioned JSON document (the *format definition*) with stages, edges between them, rank chains, series lengths, scoring, rule cards and bilingual text. The library validates such a document, type-checks its expressions, computes what it implies (how many players reach each stage, how many rounds it plays, how big a bracket is) and reports what is wrong with it as **diagnostics**: a code, a severity, a JSON pointer and flat params, often with a one-click fix expressed as a JSON patch.

The Format Studio builds on the kit. A descriptor turns a live league into a definition (`describeLegacy`), the compiler checks it, and the admin pages (`/admin/formats`, and a Format tab on the league admin page) show a stage outline, the rules text in English and German, diagnostics in plain words and a coverage line. Behind the pages there is a **storage and server layer** (see Database and API): format definitions with drafts and immutable published versions, routes to create, save, publish, fork, share and delete them, and routes that attach a published version to a league of the type **Custom format** and create one phase per format stage. On top of that the Studio has an **editor** (see Editor): admins start a format from a blank document, an example, a league's structure or a `.json` file, edit it in a form with a live Issues, Rules and Schedule preview, save it with a revision check, publish it and share it. A league admin attaches a published version to a custom league in the Format tab, and a **readiness checklist** says what the league still needs before it can start (see Attach and readiness). Since the engine release (Phases 2b to 4) the kit also **runs**: the **format engine** (`src/lib/format-engine`) computes standings from the stage's scoring and rank chain, pairs the rounds (Swiss, round robin legs, filtered, bipartite, challenge ladders), forms groups, advances players along the edges and ends stages, and the **format runtime** (`src/lib/format-engine/runtime`) runs the Phase 3 and 4 primitives of an attached format: attributes, domains, relations (a secret santa), resources, events and effects, player actions, assisted checks, manual adjustments, a stage calendar with deadline policies, team constraints with a post-match audit, and the challenge ladder. Guarded routes and two surfaces expose it: a player page and a **Live** tab for league admins (see Format engine and runtime, Live format routes). What is still **not built**: there is no mock-standings preview, sentence builder, flow canvas or simulator, no `acquire.draft` (the only reserved primitive), and admins cannot act for a player. A league runs on the kit only while its `season_formats.engine` is `kit`; on `legacy` and `shadow` the phases are ordinary classic phases and attach reports what the kit would have run.

What it gives a caller:

- `validateFormatDefinition(input)`: bounded, strict validation with the same result on the server (zod) and in the browser (a hand-written interpreter of plain data, no zod).
- `compile(input, env)`: validation, structure checks, stage graph with cycle detection, participant-flow plan, per-stage and per-edge checks, expression type checks and derived capabilities, memoised by content hash.
- `renderDiagnostic(d, locale, definition?)`: the sentence for a diagnostic, after the cached read.
- `describeDefinition(def, locale, opts?)`, `describeStage`, `definitionToPlainText`, `computeCoverage` and `describeCoverage`: the whole definition as readable text, with a coverage count (see Rules text renderer).
- `estimateSchedule(result, { players, roundDays })` and `minRosterFor(def)`: a pure schedule estimate (rounds, matches, byes, weeks) from a compile result, and the smallest roster a format needs (see Schedule estimator).
- A safe expression language for conditions (an edge's *threshold* selection today): a stored JSON AST, a text grammar, a static checker and an interpreter with hard limits.
- A primitive registry (manifest as plain data, server params schemas, per-primitive descriptions in both languages).
- Outside the kit, `src/lib/format-studio/` reads a league into a definition (`describeLegacy`) and shapes compile results for the pages (`FormatView`); see Reading a league and Format Studio pages.

### Document model

A definition is a plain JSON object. The schema is **strict**: an unknown key at any level is an issue. There is no open record anywhere; every collection is an array with a key field, and lookups go through a `Map`, so a key such as `constructor` is ordinary data.

| Section | Content | Limits | Default |
|---|---|---|---|
| `schema_version` | the literal `1` | required | none |
| `identity` | `name` (LText), optional `summary` (LText), optional `based_on` (slug) | | none |
| `stages` | stage objects | 1 to 50 | none |
| `edges` | advancement between stages | 0 to 100 | `[]` |
| `views` | cross-stage standings views | 0 to 8 | `[]` |
| `rules` | rule cards | 0 to 200 | `[]` |
| `text.sections` | titled text blocks | 0 to 32 | `{ sections: [] }` |
| `theme` | `{ world: 'auto' or a key }` | | `{ world: 'auto' }` |
| `modules` | legacy modules | 0 to 3 | `[]` |

A **stage** has a `key`, a `name`, a `participants` selector (`roster` with seeding `rating`, `random`, `manual` or `signup` and an optional `expected_count` of 2 to 4096; or `edges` with seeding `edge_order`, `rating`, `random` or `manual`), optional `groups` (`count` 2 to 26, `method` `serpentine` by default), a `pairing`, a `series`, a `ruleset` (`{ kind: 'season_default' }` by default, `{ kind: 'ruleset', id }` naming a stored ruleset DEFINITION, or `{ kind: 'preset', preset }` naming a catalog rule preset such as `gen9ou`, which only pre-picks the stage's battle settings: doubles, players per match and, for VGC, best of 3; nothing is locked), `doubles` (false), `players_per_match` (2 to 8, default 2), `scoring`, `rank` (0 to 12 steps, `[]`) and `columns` (0 to 12 metric keys, `[]`).

| Part | Fields and limits |
|---|---|
| `pairing` | `round_robin` (`legs` 1 to 4, `mirror_legs` true), `swiss` (`rounds` 1 to 32 or `auto`, `avoid_repeats` true), `single_elim` (`third_place` false), `double_elim` (`bracket_reset` false), `manual` |
| `series` | `best_of` 1 to 15 (an even number is representable and rejected by the compiler), `allow_draw` false, `overrides` 0 to 32 of `{ round 1..64, from 'start' or 'end' (start), best_of 1..15 }` |
| `scoring` | `win`, `loss` (0), `bye` (0), optional `draw` and `forfeit`; finite numbers with an absolute value of at most 1000 |
| `rank` step | `metric` (`metric` key and `direction` `desc` or `asc`), `head_to_head` (`pairwise` or `mini_table`), `coin_flip`, `decision_match`, `manual` |
| `edge` | `key`, `from`, `to`, `select` (1 to 4), `seeding` (`rank`, `cross_group`, `random`, `manual`; default `rank`), `gate` (`admin_confirm` or `auto`; default `admin_confirm`) |
| `select` | `top_n` (1 to 1024), `per_group` (1 to 64), `wildcard` (1 to 1024), `bottom_n` (1 to 1024), `manual_list` (optional `count` 1 to 1024), `threshold` (a boolean expression) |
| rule card | `rule.custom` with `id`, `text`, `scope` (`season` or one stage), `verify` (`admin_checklist`, `player_attest`, `none`), `when` (`once`, `per_match`, `per_matchday`), `visible_to_players` (true) |
| legacy module | `module.legacy` with `adapter` (`epb`, `legacy_draft`, `core_liga`) and up to 64 `facts` |

Keys match `^[a-z][a-z0-9_]{0,31}$`. The whole document must fit 262,144 bytes, 150,000 JSON nodes and a nesting depth of 64; this is checked by an iterative walk **before** any recursive parsing, so a hostile body cannot overflow the stack. Strings never contain a NUL character (Postgres `jsonb` cannot store one).

**Reserved names.** One primitive is still reserved: the stage field `acquire` (`acquire.draft`). A document that uses it, even empty, gives a `not_available_yet` issue at its pointer and nothing else is reported for that subtree. Every other section and kind the model reserved in Phase 1 is now available (see Phase 3 and 4 sections).

**Unknown rule kinds degrade.** A rule entry whose `kind` looks like a kind but is neither known nor reserved is kept as a `rule.custom` card (an Honor card): `degraded_from` holds the original kind, `text` is the entry's own text when it is valid and otherwise the kind name, and the validators report a `unknown_primitive` note, which compile turns into a `rule_unknown_primitive` warning. Every other key of such an entry is dropped without being read by name.

**Phase 3 and 4 sections.** All are optional with no default, so a document without them keeps its content hash and the golden snapshots do not move.

| pairing `bipartite`, `filter`, `challenge` | players split by an enum attribute into side A and side B with a fixed number of rounds; a Swiss or round robin base with an `allow` expression over the pair; a ladder with `rank_range`, `max_open`, `cooldown_rounds`, `accept_window_hours` | |

### LText and the fallback order

All user-facing text in a document is an `LText`: `{ en?, de?, base }` where each language is `{ v, s }` (`v` 1 to 4000 characters, `s` `human`, `machine` or `reviewed`) and `text[base]` must exist. `resolveLText(text, { viewer?, seasonLanguage? })` returns the first present value in this order: the viewer's language, the season language, the base language, then English, then German; it also says whether it had to fall back. Viewerless callers (exports, notifications) pass no viewer. The order is by language only: a `machine` text in the wanted language still beats a `human` text in another one, and the UI marks machine text. `ltext(base, en, de)`, `missingLocales`, `isTranslated`, `markReviewed` and `withTranslation` never mutate their input.

### Expression language

Conditions are stored as a JSON AST and shown as text. The AST has the node kinds `num`, `bool`, `str`, `ref`, `neg`, `arith`, `fn` (`min`, `max`), `clamp`, `round`, `cmp`, `and`, `or`, `not`, `if`, `in`, `rel`, `rand` and `agg` (`count`, `sum`, `min`, `max`, `any`, `all` over a named collection with optional `of` and `where`). Every `ref` carries its type (`number`, `boolean`, `text`).

Text grammar, lowest to highest precedence:

```
or     := and ('or' and)*
and    := not ('and' not)*
not    := 'not' not | cmp
cmp    := sum (('<' | '<=' | '>' | '>=' | '==' | '!=') sum)? | sum 'in' '[' literal (',' literal)* ']'
sum    := term (('+' | '-') term)*
term   := unary (('*' | '/') unary)*
unary  := '-' unary | primary
primary:= NUMBER | STRING | 'true' | 'false' | REF | '(' or ')' | call | aggregate
call   := ('min' | 'max') '(' or (',' or)+ ')' | 'clamp' '(' or ',' or ',' or ')' | 'round' '(' or [',' INT] ')'
        | 'if' '(' or ',' or ',' or ')' | 'rel' '(' KEY ',' or ',' or ')' | 'seeded_rand' '(' KEY ')'
aggregate := ('count' | 'sum' | 'min' | 'max' | 'any' | 'all') '(' KEY ['of' or] ['where' or] ')'
```

Comparison is non-associative. A reference is a key, or `item.field` inside an aggregate's `of` and `where`. `min(` and `max(` followed by a collection name and `of`, `where` or `)` is an aggregate; anything else is the n-ary call.

**Typing.** A `ref` must carry the type the environment declares. Arithmetic, `neg`, `min`, `max`, `clamp`, `round` and the ordering comparisons take numbers; `==` and `!=` take two values of the same type; `and`, `or`, `not` and the condition of `if` take booleans, and both branches of `if` have one type; `in` needs a homogeneous literal set of the operand's type; `rel` takes a known relation and two texts. `count` takes only `where`; `sum`, `min` and `max` need `of` (a number); `any` and `all` need `where` (a boolean) and forbid `of`. An aggregate inside an aggregate and `item.` outside one are errors.

**Evaluation.**

- `a / b` is `0` when `b` is `0`. Every literal and every intermediate result must be finite and within plus or minus 1e9, otherwise the expression fails with `expr_number_range`.
- `round(x, d)` rounds half away from zero to `d` digits (0 to 6) with integer-safe scaling.
- `clamp(x, lo, hi)` is `max(lo, min(x, hi))`: when `lo > hi`, `lo` wins.
- `min`, `max`, `sum` and `count` over an empty collection are `0`; `any` of an empty collection is `false` and `all` is `true`. Rows are visited in the order the caller gives them.
- Text is compared with `==` and `!=` only, by UTF-16 code units.
- `and` and `or` short-circuit, `if` evaluates one branch, and only the nodes actually evaluated are charged.
- `seeded_rand(key)` is a deterministic value in `[0, 1)` of `(seed, scope, key)` (a 32-bit string hash and one mulberry32 step); the test vectors are pinned, so a change is a deliberate, breaking one. `rel(name, a, b)` asks the environment's relation and is `false` for an absent pair.

**Limits.** Depth 12 (the root is depth 1), 200 nodes (literals in `in` sets and the `round` digits do not count), a step budget of 5,000 (one step per node visited and per aggregate row), numbers within plus or minus 1e9, string literals up to 64 characters, source text up to 2,000 characters, 2 to 8 arguments for `min`, `max`, `and` and `or`, 1 to 32 members in an `in` set, parser nesting 64. The compiler checks them statically (the worst case of an aggregate is its collection size times the cost of its body); `evaluate` re-checks them at run time and never throws. The document schema accepts a little more (256 nodes, depth 32) so zod only ever recurses over a bounded tree; the compiler then reports `expr_depth` or `expr_nodes` for anything above the real limits.

**Deliberately absent:** user-defined functions, lambdas, loops, any way to turn a string into code, clocks, randomness other than `seeded_rand`, I/O and regular expressions built from input.

### Registry contract

The registry is the list of *primitives*, the building blocks a format is made of (a pairing, a series rule, a rank step, an advance rule, a rule card, and so on). A kind is `<family>.<name>`, for example `pairing.swiss` or `advance.top_n`.

- **Manifest** (`registry/manifest.ts`): one plain-data entry per kind with its slot, tag, **level**, availability, phase, catalog keys and, for available kinds, its **Spec**. The Spec DSL (`registry/spec.ts`) describes shapes as data: `bool`, `int`, `num`, `str` (with a named pattern `key`, `slug`, `uuid` or `kind`), `enum`, `ltext`, `expr`, `obj`, `arr`, `union` and `oneof`. `DOCUMENT_SPEC` is built from the manifest, and `validate.browser.ts` interprets it. No pattern string from input is ever compiled.
- **Server entry** (`registry/server.ts`): for each available kind its manifest entry and the zod params schema. The document schema composes its unions from the same exports, so the two cannot diverge.
- **Levels** state the intended enforcement. **Auto**: the engine runs it. **Checked**: the engine computes a result and an admin confirms it. **Honor**: a rule card nobody enforces (`rule.custom`). The level is metadata for the builder and the coverage line; the engine runs the `auto` kinds of a league on the kit engine, and a team constraint is **Checked** (advisory while a team is built and saved, audited after the match, confirmed by an admin).
- **53 kinds are available** and 1 is reserved (`acquire.draft`). Phases 1 and 2: `stage.define`, `group.form`, the five classic pairings, `series.rule`, `team.ruleset`, `score.match`, the five rank kinds, `standings.view`, `advance.rule` and its six selections, `rule.custom`, `text.rules`, `theme.hint`, `module.legacy`. Phase 3: `attr.define`, `attr.assign`, `domain.define`, `relation.define`, `resource.define`, `metric.define`, `track.progression`, `score.placement`, `rule.on_event`, `effect.apply`, `player.action`, `check.assisted`, `adjust.manual`. Phase 4: `pairing.bipartite`, `pairing.filter`, `pairing.challenge`, the six `constraint.*` kinds (`roster_size`, `count`, `distinct`, `type_quota`, `tera`, `evolution_stage`), `time.schedule`, `time.deadline_policy`, `stage.end_when`, `stage.foreach_group`. A reserved kind exists in the manifest only; a document that names it fails with `not_available_yet`.

**Adding a primitive** takes one registry entry (kind and Spec in the manifest), its zod params schema in `schema/primitives.ts`, its describe function in `registry/describe.ts`, its keys in `format-studio/primitives` (label, summary, describe, fields, options) in both languages, and tests: the registry test checks that every available kind has a server entry and that every key exists in both languages.

`describePrimitive(kind, node, locale)` renders a validated node as one sentence. It never throws: an unknown kind, a reserved kind or a node of the wrong shape gives the label of the kind.

### Compile pipeline

`compile(input, env = CURRENT_ENV)` returns `{ ok, hash, definition, diagnostics, capabilities, graph, plan }`:

1. Inspect the input (iterative, bounded) and hash its canonical form. Input that is not JSON, or is too deep, too large or has too many nodes, gives one `schema_type` or `schema_limit` diagnostic and nothing else.
2. Look the result up by `inputHash|envKey`. The same document in another key order is the same input, and a different environment is a different entry. The cache is an LRU of 32 results; `clearCompileCache()` empties it.
3. Validate. An invalid document yields `schema_*` diagnostics only; no later phase runs and `definition` is `null`.
4. Notes become `rule_unknown_primitive` warnings.
5. Structure checks. 6. Stage graph. 7. Plan. 8. Stage checks. 9. Edge checks, including the expression type check of every threshold. 10. Translation coverage. 11. Capabilities.
12. Diagnostics are sorted (error, warning, info; then pointer; then code), the result is deep-frozen and stored. `hash` is the content hash of the **parsed** definition (defaults applied).

Compile is pure: no clock, no randomness, no I/O. The result holds codes and params only, never localized text, so a cached result is locale-free and rendering happens after the read.

**Plan conventions.** A roster stage starts from `env.rosterSize`, else `expected_count`, else it is unknown (and gets one `participant_count_unknown` note). An edge sends `min(n, source)` for `top_n`, `n * groups` for `per_group`, `n` for `wildcard` and `bottom_n`, `count` for `manual_list` (unknown without one) and `0` to the source size for `threshold`; the selections of an edge add up, and so do the edges into a stage (they are assumed to be disjoint). Round robin plays `legs` times the round count of the production helper (`n` rounds for an odd group, `n - 1` for an even one, none below two players); Swiss plays its rounds or `ceil(log2 n)` for `auto`; single elimination `ceil(log2 n)` rounds with the third-place match kept inside the final round; double elimination `2 * ceil(log2 n) - 1`, plus one with the bracket reset. A bracket is the next power of two and the byes are the difference. A count the plan cannot know is `null`, and a check that needs it does not run.

**`CompileEnv`** describes what the product can do today:

```ts
interface CompileEnv {
  matchModel: { draws: boolean; forfeits: boolean; maxPlayersPerMatch: number };
  features: { killStats: boolean; rating: boolean };
  rosterSize?: number;
  rulesetIds?: ReadonlySet<string>;
}
```

`CURRENT_ENV` in `engine/env.ts` says draws are **off**, forfeits are **off** and a match has **two** players, because a match still needs a winner to complete and finalizing writes no draw. That file is the only place those three values live: when the match-model change lands they flip there and the diagnostics `draws_unsupported`, `forfeits_unsupported` and `players_per_match_unsupported` go quiet with them.

The reasons are `unknown_metric`, `needs_kill_stats`, `needs_rating` and `needs_opponents`.

The threshold expression on an edge sees the standings of its **source** stage: the references `points`, `wins`, `losses`, `games_played`, `rank`, `group_rank` and `participants` (plus `kill_differential` and `buchholz` when the stage produces them), and the collection `standings` with the same fields, sized by the plan (256 when unknown). Its result must be boolean.

**Fixes** never invent data the user has to choose: a diagnostic that needs a choice carries no fix. A fix is offered only when applying it adds no error: no fix removes the only rank step of a table stage or adds a step or selection beyond the document limits. Patches use `add` for members a stored document may leave to the schema's defaults and `replace` or `remove` only where the diagnostic proves the member exists.

### Client/server split

The browser may import `src/lib/format-kit/client.ts`. Its import closure holds **no zod, no `server-only`, no `@pkmn`, no `next`, no React and no Supabase**; it reaches outside the kit only for the i18n runtime (`core`, `config`, `format`, `define`, `types`), the two kit catalogs, `@/lib/season/format-capabilities` (type imports only) and `@/lib/tournament/round-robin` (pure, imports only its types). `client-boundary.test.ts` walks that closure and fails on anything else, and on any server file of the kit.

Server code imports `index.ts`, which adds the zod schemas (`schema/`, `expr/schema.ts`), the zod validator, the server registry and the zod compile entry. Both validators return the same `ValidationResult` (same issues in the same order, same normalised value, same notes), and a seeded fuzz test holds them together. `validate.browser.ts` is not an alias of the server file: `client.ts` imports it (and `compile.browser.ts`) by relative path.

**Decision: no bundler alias.** Client code imports `@/lib/format-kit/client` and nothing else from the kit. The `format-pack` alias exists because server and browser import the *same* specifier; the kit has two entry files instead, so the entry file is the boundary. The Studio client-boundary test (`src/components/format-studio/__tests__/client-boundary.test.ts`) enforces it: every `use client` file under `src/components/format-studio` and `src/app/admin/formats` must reach no zod, `server-only`, `@pkmn` or Supabase, none of the kit's server files, and must not import the bare `@/lib/format-kit` specifier. The loader and the pages (server) import the server barrel and are never imported by a client module. The editing core under `src/lib/format-studio/editor/` is client code too: `editor-boundary.test.ts` walks its closure and fails on zod, `server-only`, `@pkmn`, Supabase, a kit server file or the loader, and checks that each file reaches the kit through `@/lib/format-kit/client` only. `materialise.ts` (`planStages`, used by the attach preview in the browser) keeps its own `STAGE_NAME_MAX_CHARS` constant instead of importing the zod-based field limits, so it stays inside that closure; a test pins the constant to the field limit.

### Capabilities derivation

`deriveCapabilities(definition)` returns the same 15 flags as `getFormatCapabilities` in `src/lib/season/format-capabilities.ts`. A kit document starts with **every flag off**, on purpose different from the legacy baseline (`participantTypeAssignment` and `typeCores` are on there): attributes, cores and drafts do not exist in a kit document. Each `module.legacy` adapter then turns on the flags of the legacy format it stands for, flag by flag (`epb` is `evolution_point_buy`, `legacy_draft` is `draft`, `core_liga` is `singles`).

### Rules text renderer

`engine/describe-definition.ts` turns a whole definition into readable text. It is pure, client-safe and exported from both barrels. Every function is total: nothing throws, a missing stage key gives `null`, and a malformed node falls back to its key or kind label.

| Function | Result |
|---|---|
| `describeDefinition(def, locale, opts?)` | a `DefinitionDescription`: `title`, `summary`, an `overview` sentence, one `StageDescription` per stage, the `advancement` sentences, `views`, `rules` (one `RuleCardDescription` per rule card), `modules` (label, summary and facts), `sections`, the `coverage` numbers and the `coverageLine` sentence |
| `describeStage(def, stageKey, locale, opts?)` | one `StageDescription` (name, summary, participants, groups, pairing, series, ruleset, scoring, doubles, rank steps and chain, expected counts, incoming and outgoing edge sentences), or `null` for an unknown key |
| `definitionToPlainText(description)` | the description as plain text: title, overview, the stage blocks, advancement, rules, modules (`label: value`), sections and the coverage line, under headings from the catalog; deterministic, no timestamps |
| `computeCoverage(def)` | the locale-free `Coverage` numbers (below) |

`DescribeOptions` has three optional parts. `plan` (the `plan` of a compile result) adds an `expected` sentence to each stage it has an entry for: the participant range, the rounds, and the byes or bracket size; without an entry `expected` is `null`. `order` (the `graph.order` of a compile result) sets the stage order; stages missing from it are appended in declaration order, and without it the declaration order is used. `rulesets` maps a stored ruleset id to its name for the ruleset sentence; an id it does not know reads as the generic "specific ruleset" sentence.

Names resolve with `resolveLText(text, { viewer: locale })`. The sentences for a stage, its pairing and series, a team ruleset, a group form, an advance rule, a rule card, a view and a legacy module come from `describePrimitive`; the rest (overview, participants, plan, edge, rule words, coverage, headings) from the `format-studio/describe` catalog. An advance rule shows stage **names**, never keys. Plural forms are `{one, other}`.

**Coverage.** `computeCoverage` returns `{ auto, checked, honor, legacy, total }`. The units are counted from the definition:

| Bucket | What counts |
|---|---|
| `auto` | per stage one pairing, one series and one scoring; one for the groups when the stage has them; one per rank step; one for a stage ruleset that names a stored ruleset or a rule preset; one for `end_when` and one for `foreach_group` when present; one for a calendar plus one per deadline policy; per edge one for each selection whose gate is `auto`; one per view; one per rule whose kind is `auto` (other than `check.assisted` and `adjust.manual`); one per attribute, domain, relation, resource and metric entry. Each unit counts by the level its kind has in the manifest, so a kind marked `checked` or `honor` moves out of this bucket |
| `checked` | each selection of an edge whose gate is `admin_confirm` (the engine computes the result, an admin confirms it); one per stage team constraint (`constraint.*`: advisory while a team is built, audited after the match, confirmed by an admin); one per `check.assisted` and one per `adjust.manual` rule |
| `honor` | one per rule card (`rule.custom`): nobody enforces it |
| `legacy` | one per `module.legacy` |
| `total` | the sum of the four |

`coverageLine` is a catalog sentence that lists only the non-zero buckets (for example "7 automated, 2 confirmed by an admin, 1 honor rule, 1 legacy module"); a definition without any unit gets the "no rules" sentence. `describeCoverage(coverage, locale)` renders the same sentence from stored numbers (the gallery uses it for the list cards). The numbers say how the *document* is classified, not what the engine runs today.

### Reading a league: describeLegacy

`src/lib/format-studio/legacy/describe-legacy.ts` turns the live rows of one league into a read-only `FormatDefinition`. It is pure: no locale argument, no I/O, it never throws and never mutates its input. Both languages are written into the output texts, so the result is locale-free and can be sent to the browser; rendering happens later with the viewer's language. The output survives a JSON round trip unchanged and validates in strict mode (optional fields are omitted, never `undefined`). Numbers are clamped into the kit ranges but semantics are not corrected: an even best of stays even and the compiler reports it.

**Input** (`LegacyInput`, `legacy/types.ts`):

| Part | Content |
|---|---|
| `season` | id, name, description, `formatType`, `language`, ruleset id and name, `routeTheme`, participant count, core pool size (or `null`), league group count |
| `stages` | per phase: id, name, `bracketType`, `stageOrder`, `bestOfDefault`, `boOverrides`, `isDoubles`, ruleset id and name, `advancementRule`, `enrollmentSource` (type and source phase id only), `bracketResetEnabled`, group count |
| `pack` | the Evolution Point Buy pack values the descriptor needs (`matchPoints`, `tiebreakerChain`, `teraByStage`, `defaults`, `stageLock`, `participationPoints`, `comeback`) |
| `facts` | per-format extras: `typeAssignments` (gym-typed and cored counts) or `null`, `formatRules` or `null`, `draftTierLimits` or `null` |

Pack values enter only through `input.pack`; `describeLegacy` does not import the pack module, so tests inject literals.

**Stages.** Stages are sorted by `stageOrder` (stable by input order) and the first 50 are kept; keys are `stage_1` to `stage_n`. The definition's name is the league name; its summary is the league description when that is not empty. Every name taken from the database (league, phases) becomes an `LText` with the same cleaned string in English and German (NUL removed, trimmed, cut to 4000 characters; an empty phase name falls back to the catalog's "Phase n"), with `base` set to the league language, so no "untranslated" note is raised for proper names. `theme.world` is the league's route theme when it is a valid key, else `auto`. A league without phases gives `stages: []`, which is invalid by design; the loader never compiles it.

| Legacy `bracket_type` | Kit pairing |
|---|---|
| `round_robin` | `round_robin`, `legs` 1, `mirror_legs` true |
| `swiss` | `swiss`, `rounds` `auto`, `avoid_repeats` true |
| `single_elim` | `single_elim`, `third_place` false |
| `double_elim` | `double_elim`, `bracket_reset` = `bracketResetEnabled !== false` |

The series is `best_of` = the phase default with `allow_draw` false. A stage is doubles when the phase flag or the league format says so (`players_per_match` stays 2). The ruleset is `{ kind: 'ruleset', id }` when the phase names a uuid different from the league's ruleset, else `season_default`.

**Groups.** A stage has groups when its own group count is at least 2; a round-robin stage without its own groups inherits the league group count when that is at least 2 (phases mirror the league groups, which may not be generated yet). The count is capped at 26. The method is `manual` when the league has groups (they are placed in the league groups editor), else `serpentine`. Fewer than 2 groups give no `groups` field.

**Participants and edges.** Stage 1 takes `{ from: 'roster', seeding: 'manual' }`. For a later stage *k*:

| Case | Result |
|---|---|
| (a) enrollment source `standings` whose source phase is an earlier kept stage *S* | an edge *S* to *k*; the selection is *S*'s advancement rule, or a `manual_list` when it has none |
| (b) no enrollment source, or one that is not `roster`, and stage *k-1* has an advancement rule with a count of at least 1 | an edge *(k-1)* to *k* with that rule |
| (c) otherwise | `{ from: 'roster', seeding: 'manual' }` and no edge |

A stage with an incoming edge takes `{ from: 'edges', seeding: 'edge_order' }`. An advancement rule becomes `per_group` (`n` clamped 1 to 64) when it is per group, else `top_n` (`n` clamped 1 to 1024); the edge has seeding `rank` and gate `admin_confirm`. Edge keys are `advance_{from}_{to}`. **The rule stored on a phase is read as the edge out of that phase**, as the phase form hint and the phase timeline do. A rule that no edge consumes (the last phase, or a next phase enrolled from the roster) becomes a text section, so nothing is dropped silently.

**Series overrides.** Legacy overrides are keyed by English round names. Names the kit can express become overrides; everything else becomes a bilingual text section `bo_stage_{k}` (one line per entry, bound to the stage).

| Phase type | Name | Kit override |
|---|---|---|
| `single_elim` | `Finals` | round 1 from `end` |
| `single_elim` | `Semifinals` | round 2 from `end` |
| `single_elim` | `Quarterfinals` | round 3 from `end` |
| `round_robin`, `swiss`, `single_elim` | `Round N` (N from 1 to 64) | round N from `start` |
| anything else (double elimination names, unknown names, N out of range) | | text section |

Overrides are sorted by round, then direction; at most 32 are kept; `best_of` is clamped 1 to 15.

**Scoring and rank.** This characterises today's code: the league hub and `computeStandings` for tables, `lib/tournament/byes.ts` for byes.

| Stage | Win | Loss | Bye | Rank |
|---|---|---|---|---|
| round robin (not Evolution Point Buy) | 3 | 0 | 0 | points, KO differential, Buchholz, wins (all descending; the `computeStandings` order) |
| Swiss (not Evolution Point Buy) | 1 | 0 | 1 (a Swiss bye scores as a win) | the same four steps |
| single or double elimination | 1 | 0 | 0 | none |
| table stage of an Evolution Point Buy league (round robin and Swiss) | the pack's match points for a win | 0 | 0 | the league's stored tiebreaker order when it is usable, else the pack's tiebreaker chain, step by step (below) |

The Evolution Point Buy rows use the helpers the standings use (`effectiveMatchPoints` and `effectiveTiebreakerChain` in `src/lib/tournament/standings-rules.ts`), so the description and the tables cannot drift apart. The stored order is `format_rules.tiebreaker_order`, edited on the league's Rules tab; an order the standings cannot use (empty, an unknown or repeated step, a decision match that is not last, or only a decision match) falls back to the pack's chain. A stored order without a decision match leaves ties open, and the compiler says so (`rank_open_ended`, a warning).

`draw` and `forfeit` are never set. The chain steps map as: `match_points` to points descending, `kill_difference` to KO differential descending, `head_to_head` to head to head (pairwise), `decision_match` to the decision match. `evolution_points` has no kit metric and is **omitted from the rank**; its position is kept as an Evolution Point Buy module fact.

**Modules and facts.** A module carries data only (`module.legacy` facts: a label and a string, number or boolean value; at most 64 per module) and never claims that the kit runs it. At most one module per adapter. Fact labels come from the `format-studio/legacy` catalog in both languages.

| Module | Present when | Facts |
|---|---|---|
| `core_liga` | the format is singles, doubles or draft **and** (the core pool is set, or any participant has a core, or any has a gym type) | core pool size, cores assigned and gym types assigned (the last two only when the counts were read), roster size |
| `legacy_draft` | the format is draft | the limit of each tier that has one |
| `epb` | the format is Evolution Point Buy | match points for a win; the 1-based position of each tiebreaker step in the order the standings rank by; Tera by stage 1 to 3; draft budget, picks, token ratio, token maximum and token maximum per line (from the format rules row or, without one, the pack defaults); whether the redraft is open; counts of banned moves and banned items; stage lock (enabled, stage, by matchday, suspended matchdays); participation points per matchday and until which stage; the Comeback earn window |

The capabilities derived from an Evolution Point Buy or draft descriptor equal `getFormatCapabilities` of that format; the `core_liga` descriptor's capabilities are a subset of the singles ones.

**Known approximations.**

- **Evolution points tiebreak.** The step is not in the kit's metric table, so the rendered Evolution Point Buy rank chain lacks it. Its position is in the module facts, and the golden snapshot makes the gap explicit. Registering it as a metric would close the gap.
- **Round-name overrides.** Only `Finals`, `Semifinals`, `Quarterfinals` and `Round N` map to round indexes. Double-elimination overrides are shown as text, not machine-readable.
- **Advancement direction.** The descriptor follows the phase form (the stored rule is the edge out of the phase). The enrollment sync reads the rule from the target phase. The descriptor shows the stored rule either way, and a rule nobody consumes appears as a text section. Auditing the direction is separate work.
- **Scoring split.** Round robin scores 3 per win, Swiss 1 per win with the bye scored as a win, and an Evolution Point Buy round-robin or Swiss table scores the pack's match points for a win with no bye points. The descriptor mirrors that split; a later single scoring specification must not change the golden snapshots silently.
- **Real leagues can compile with errors or warnings** (an even best of, a top N larger than the roster, per-group advancement before phase groups exist). They are shown in plain words, not hidden. `env.rosterSize` and the inherited league groups reduce the noise; only the fixtures must compile without errors.
- **Stored references only.** The ruleset shown is the one stored on the league or phase; the name-match fallback of the effective-ruleset lookup is not applied, so no extra read happens.

| `/admin/formats/[id]/edit` | the owner and site admins | the editor; anyone else who may view the format is redirected to the read-only page |

The league admin page shows the same content as a **Format** tab (`?tab=format`, every format, variant `tab`) with a link to the detail page. A **custom** league's tab adds, above the outline, the readiness card and the attach panel (see Attach and readiness); the overview tab of a custom league shows the readiness card too.

**Loader** (`format-studio/loader.ts`, server only). `loadLeagueFormat(league)` runs one wave of at most five reads: the league's stages, the stage group counts, the league group counts, and per format the type-assignment counts (singles, doubles, draft), the format rules (Evolution Point Buy) or the tier limits (draft). The league row comes from the caller. It returns `{ kind: 'no_phases' }` without compiling when there are no stages, otherwise `{ kind: 'ok', view, editorLinks }`; `editorLinks` point to the tab where each module is edited (rules for `epb` and `legacy_draft` when the format has that tab, participants for `core_liga`). `loadLeagueFormatSummaries(leagues)` makes three reads for any number of leagues (stages by season ids, chunked by 50 and paged past 1000 rows; stage group counts; league group counts) and adds the type-assignment counts of each classic league without a core pool, because they decide whether the Core Liga module exists and a module is one unit of the coverage line; the other per-league extras (format rules, tier limits) are not read, and modules add no diagnostics, so the error and warning counts are not affected. `presetViews()` compiles the four presets once per process. Nothing goes through a cache: the data is admin-only, and rendering stays after the read.

**`FormatView`** (`format-studio/view.ts`, client-safe, plain JSON, no locale) is the shape the pages hand to the browser: `ok`, `hash`, `definition`, `diagnostics`, `plan`, `order` (the graph order followed by any stage key missing from it), `capabilities`, `coverage` (`null` without a definition) and the `rulesets` names. `toFormatView(result, extras)` copies a frozen compile result into it; `legacyCompileEnv(participantCount)` is `CURRENT_ENV` with `rosterSize` set only for two or more participants.

**Client component.** `FormatDetail` is the one `use client` entry: title and summary, a counts badge, the stage outline, the rules text with an EN/DE toggle (it starts in the viewer's language; the state is the language key, never translated text; `aria-pressed` on the buttons), the diagnostics in plain words (errors first; no one-click fixes because nothing is editable), the coverage line and the module facts with the editor links. It renders with `describeDefinition` and `renderDiagnostic` in the browser, so both languages of the kit catalogs ship on these admin routes only.

**Golden master.** `src/lib/format-studio/__tests__/golden.test.ts` snapshots, for five generic fixture leagues (`fixtures/leagues.ts`: groups and playoffs, doubles, draft with double elimination, Evolution Point Buy, Core Liga style): the JSON of `describeLegacy`; the server compile result (`ok`, hash, diagnostic codes with severity and pointer, coverage, capabilities); and the plain text of the rules in English and German. Every fixture must compile with `ok` and no error. Later phases must keep these snapshots unchanged. Changed copy (a fact label, a sentence) is updated on purpose: run `npx vitest run src/lib/format-studio -u` and review the diff before committing.

### Editor

The editor is a form over a plain JSON document. Its logic is pure and lives in `src/lib/format-studio/editor/`; the components only compose it. The generic half is shared with the Ruleset Studio: the editor request, state and target helpers sit in `src/lib/studio-core` (`request`, `editor-state`, `targets`), and the frame, toolbar, the five dialogs (publish, share, fork, delete, changed-elsewhere), the unsaved-changes guard, `useDraftEditor` and the library cards are `src/components/studio-shell` (`FormatCard` is `studio-shell/library/LibraryCard`; `useFormatEditor` is `useDraftEditor` plus the format's compile, rows and counts). Format-specific bindings stay in `format-studio` (`access`, `slug`, `api-body`, `document-guard`, `document`: the new-format skeleton).

- **Starts.** A new format begins from a blank document (name and authoring language), a shipped example or a gallery format (a fork), a league's structure, or an imported `.json` file. "Copy a league's structure" is a button on `/admin/formats/league/[id]`; the New format dialog links there. The copy drops the league's module facts and resets named rulesets to the league default, because both carry league tuning values and per-community ids; the name and the rules text are kept.
- **Document model.** A stored draft is any JSON object. `normalizeDraft` fills the schema defaults for missing optional members, keeps unknown members untouched (the Issues tab offers to remove them) and refuses only shapes a form cannot show (a list that is not a list, an item that is not an object): the editor then shows an error panel with a download link and a confirmed "replace with a blank format". The baseline for "unsaved changes" is the canonical JSON of the normalised document, so opening a draft never starts dirty.
- **Operations.** Every edit is an immutable function in `ops.ts` (stages, edges, selections, rank chain, series exceptions, Honor cards, rules text sections, identity, theme): it never mutates its input, never throws for an out-of-range index, never produces a duplicate or malformed key, and stops at the document limits (the add button is disabled with the limit as its reason). Removing or renaming a stage key cleans every reference to it (edges, rule scopes, text sections, views). Reordering uses up and down buttons with a live-region announcement; there is no drag and drop.
- **Layout.** An outline (name and summary, look, stages, advancement, Honor rules, rules text) next to an inspector for the selection, with the preview panel below it (a third column from `xl`). Below `lg` the outline collapses into a disclosure above the inspector. Every control has a visible label; an error at a field is tied to it with `aria-describedby` and `aria-invalid`, in plain words. Draw and forfeit scoring are shown disabled with the reason (a match needs a winner today). A threshold selection is shown read-only as its printed condition and can be removed; editing conditions waits for the later builder.
- **Preview tabs** (an ARIA tablist). **Issues** lists the compiler's diagnostics as sentences with a "Go to field" button and the one-click fixes (and "Remove this field" for unknown or reserved members). **Rules** is the generated rules text. **Schedule** is the estimate below, for a chosen player count and cadence. The editor compiles with the known ruleset ids, so a ruleset that no longer exists is flagged before attach does; the publish route compiles without them, so the editor is at most stricter than publish.
- **Saving.** Explicit only: **Save draft** and Ctrl/Cmd+S (no autosave: the API allows 300 draft saves per 10 minutes). The save sends the revision it started from; on `format_stale_revision` the **changed elsewhere** dialog offers Reload (discarding unsaved edits after a second confirmation), Keep mine (adopts the server revision and saves again) or Cancel. An edit made while a save is running stays unsaved. The unsaved guard asks before a `beforeunload`, before a link click and on the browser's back button: while the editor is dirty it adds one history entry for the same address, and stepping back from it asks (Stay returns to the editor, Leave goes back once more). The entry stays after a save, so the first Back then simply continues. A publish that finds a newer revision opens the same dialog, at the revision the server named. Number fields take a point or, where decimals are allowed, one comma (`0,5`); a whole-number field refuses the comma.
- **Publish, share, fork, delete.** Publish shows the compile result (errors block it, warnings do not), takes an optional English and German changelog, saves first when there are unsaved changes, and creates the next version. Share chooses private, shared with league admins, or the gallery (site admins only); sharing needs a published version. Fork makes a private copy of the last published version. Delete is offered for a draft that was never published and is not attached.
- **Import rules.** The `.json` pre-check applies the API's limits in the browser (1 MiB, depth, node count, no NUL character, an object with a valid name), reports unknown fields and reserved sections by pointer, and offers to strip them. The file is parsed, never evaluated.

### Schedule estimator

`estimateSchedule(result, { players, roundDays })` (`engine/schedule.ts`, exported from the client entry) turns a compile result into a table: per stage the participants, rounds, matches, matches per player, byes and weeks, plus totals. It is pure (no clock, no randomness; `source-safety.test.ts` scans it) and returns `null` for an invalid document.

- **Round robin** with `c` groups and `L` legs: groups of `floor(p/c)` or `ceil(p/c)` players; a group of `g` plays `L*g*(g-1)/2` matches, each player `L*(g-1)`, and an odd group has `L*g` byes. **Swiss** with `R` rounds: `R*floor(n/2)` matches and `R*(n%2)` byes. **Single elimination**: `n-1` matches (one more with a third-place match), `ceil(log2 n)` rounds, `bracketSize - n` first-round byes. **Double elimination**: `2n-2` matches, plus one for a bracket reset (the upper bound). **Manual pairing**: everything is unknown and shown as a dash. A best-of counts as one match.
- Participant counts that are ranges (thresholds) are evaluated for every integer in the range and reported as a minimum and a maximum; elimination per-player counts are bounds, not exact numbers (the `precision` field says which).
- **Weeks** are `ceil(rounds * roundDays / 7)` per stage; the total is computed from the summed rounds, so stage rounding does not accumulate. Stages are counted one after the other, which is an upper bound for stages that could overlap. A cadence outside 1 to 28 days falls back to 7, and the player count is clamped to 2 to 4096 (the UI offers 2 to 256, default 8).
- `minRosterFor(def)` is the smallest roster that lets every roster-fed stage start: the largest of `groups.count * 2` (or 2 without groups) over those stages. The readiness checklist uses it.
- The tests cross-check the counts against the real generators (`generateRoundRobinRound`, the elimination structure builders) for 2 to 33 players.

### Attach and readiness

The Format tab of a **custom** league (`FormatPanel`) shows, in order, the readiness card (`id="format-readiness"`; it is about getting ready to start, so a league that has started does not get it), the attach section (`id="format-attach"`) and, once the league has phases, the read-only outline. Every other league type keeps its tab and makes no new read.

- **Attach panel** (`FormatAttachPanel`, a client component that gets plain props only: no spec, no seed, no player row). States: **started** (the format is locked: a notice, and only the attached summary stays), **attached** (name, version, the first 12 characters of the frozen hash with the full hash in a `title` and a Copy button, the attach time, the number of phases created, a link to the source format or a note that it was deleted, and **Re-attach** and **Detach**), and **unattached or re-attaching** (the picker). The picker is a grouped select of published formats the admin may attach (yours, shared with league admins, the gallery, and for site admins other admins' formats), loaded by `loadAttachCandidates` (at most 100, with a note when capped; names only).
- **Preview.** Choosing a format fetches its published version and runs `previewAttach` in the browser: the same compile and `planStages` the server runs. The list shows the phases that will be created (order, name in the league's language, bracket type, best of, doubles, and the ruleset as "Ruleset: <name> vN", "League ruleset: <name> vN" or, for a rule preset stage, "Creates the ruleset <preset>") and the parts of the format the league's engine does not run (see Engine gaps), one plain sentence per gap code (a best-of exception with no matching round, round-robin legs, wildcard, threshold and bottom-N selections, groups, filter, bipartite and challenge pairing, constraints, a calendar, an end condition, a per-group stage). A version with errors shows one fixed sentence and a link to the format instead.
- **Stage ruleset field** (stage inspector). Three kinds: the league default, a stored ruleset (a select of `<name> vN` options, the newest published version; the help says attaching pins that version and that later versions never change a running league, with a link "Open the Ruleset Studio"), or a catalog **rule preset** (`RulesetPresetSelect`, the shared picker of `src/components/ruleset`; picking one pre-picks the doubles setting (the series length stays as it is; only a new format or an example fork sets best of 3 for VGC); the help says the preset becomes a ruleset of the league, published as version 1, which the admin can change in the Ruleset Studio and then update the league to). A ruleset id the editor does not know shows "Unknown ruleset" and the compile reports `ruleset_not_found`.
- **Buttons.** Attach (or Re-attach) is disabled, with a visible reason, when the league has started, a request is running, nothing is chosen, the preview is still loading or invalid, a stage needs the league's default ruleset and the league has none (the league ruleset cannot be changed after creation, so the fix is a format that names a ruleset for every stage), or the league has hand-made phases (the notice links to the Phases tab). The reasons are decided by `attachButtonState` in `attach-state.ts`; the API enforces the same rules. Re-attach and Detach ask first. Failures show the catalog text of the error code (the `blocked` class in a warning style); after a write the page is read again, so the card and the outline follow the server.
- **Readiness checklist** (`computeReadiness`, `ReadinessCard`): four items, each Done, To do, or Waiting for the step above, always as words (the icon is decoration): a format is attached; the phases it defines are created (and none are hand-made); enough players are registered for the format (`minRosterFor`); every stage has a ruleset. An item still to do links to the tab, and for the picker the anchor, where it is fixed. A league that is ready shows one line. The card is shown on the overview tab and the Format tab of a custom league and renders nothing for any other type.
- **What blocks.** Only the first item blocks: while no format is attached the **Active** status button is disabled and the reason is printed under the status control (`LeagueStatusControl` takes an optional `blocked` map; the current status is never blocked). The other unmet items only warn, because the API enforces only the attached format (the database trigger and the generate routes refuse a custom league without one).
- **Create flow.** Creating a league of the type Custom format opens its Format tab (`leagueCreatedHref`), where attaching a format is the first step; every other type opens the league as before.

### Database and API

Three migrations add the storage layer. Apply them in this order, before the code is deployed (the first must commit on its own, because a new enum value cannot be used in the transaction that adds it):

1. `20261024100000_season_format_type_custom.sql`: adds the value `custom` to the enum `season_format_type`. Irreversible.
2. `20261024100100_format_definitions.sql`: `format_definitions`, `format_definition_versions`, the immutability trigger and the function `format_publish_version`.
3. `20261024100200_season_formats_and_stage_columns.sql`: `season_formats`, the two `tournaments` columns, the functions `format_season_started`, `format_attach_season` and `format_detach_season`, and the trigger that keeps a custom league without a format from becoming active.

The runtime and engine migrations that follow (`20261104090000` to `20261106090000`) are listed under Format engine and runtime. Every new table has row level security on, no policy, and grants to `service_role` only; every new function revokes execute from `PUBLIC`, `anon` and `authenticated` and grants it to `service_role`. The browser never reads these tables; every access is an API route or a server read.

**Tables**

| Table | Holds |

Named constraints carry the size and uniqueness rules (`format_definitions_slug_key`, `format_definitions_draft_size`, `format_definition_versions_spec_size`, `season_formats_spec_size`); the error mapper turns a violation into a typed error by the constraint name. The size check measures the jsonb TEXT form, which is a few percent larger than the canonical JSON the kit measures, so a document just under 256 KB can pass the kit and fail the table: that answers 413 `format_document_too_large_to_store`, never a 500.

**Versioning and hash rule.** A draft is any JSON object; publishing compiles it with the kit and stores the parsed definition. `content_hash` is `contentHash(spec)` of that stored JSON. Attach recomputes the hash from the stored `spec`, never by parsing it again, so a later kit change cannot break an old version; a mismatch is a data fault (logged with ids, a generic 500, no detail to the client). Publishing a draft whose hash equals the latest version's is refused (`format_nothing_to_publish`). `format_publish_version` locks the definition row, compares `draft_rev`, numbers the version, sets `current_version_id` and refreshes the listed `name` and `description` from the published spec's identity in one transaction (the publish route then expires the `format-library` shelf, and the answer carries the refreshed row).

**Visibility and authorization.** Site admins can do everything; league and tournament admins (the "owner" tier) only ever see and change their own formats and the ones shared with all admins. The pure rules live in `access.ts`; the routes check them on the LIVE player and the definition row read from the database (`requireFormatViewer`), never on the token.

| Owner of a `custom` row | own | own | own, unless `gallery` | `private` <-> `league`, never from or to `gallery` | own |
| Another admin | `league` and `gallery` rows (summary and latest published spec only) | no | no | no | `league` and `gallery` rows |

Every write route reads its body in this order: guard, rate limit, bounded body (`readBoundedJson`: a 1 MiB raw cap, the `content-length` header checked before the body is read), the kit's `assertDocument` on the `document` member (plain JSON object, depth 64, 150,000 nodes, 262,144 canonical bytes), the strict zod envelope, and only then the database. The raw cap is above the canonical limit on purpose, so a client may send indented JSON. A draft may be an invalid format (the editor saves half-built ones); only publish and attach need a compile without an error diagnostic. Responses never contain a `players` row: an owner is `{ id, name }`. Every library write calls `expireFormatLibraryReads()`; attach and detach call `expireSeasonReads` with the created, updated and removed phase ids. Audit events (fire-and-forget): `format.create`, `format.fork`, `format.publish`, `format.visibility`, `format.delete`, `season.format.attach`, `season.format.detach`; draft saves are not audited.

**Attach.** `attachFormatToSeason` checks in this order, with bounded reads, and calls no database function when any step refuses: the league exists and is `custom` (`format_season_not_custom`); it has not started (`isSeasonStarted`: status `active` or `completed`, any phase that left `upcoming`, any phase with a round; `format_season_started`); the caller may attach the definition (`format_attach_forbidden`) and the version is published (`format_not_published`); the stored spec still hashes to the stored hash; the spec compiles without an error against the rulesets that exist and WITHOUT a roster size (`format_attach_invalid`, param `first` = the first error code; size-dependent problems belong to the readiness checklist of the editor); every `season_default` stage has a league ruleset (`format_attach_ruleset_required`); the league has no hand-made phase (`format_attach_manual_phases`). Then `format_attach_season` runs in one transaction that locks the league, repeats the started and manual-phase checks, writes `season_formats`, deletes the stages that left the spec (it proved them upcoming and round-free) and upserts the others by `(season_id, format_stage_key)`, so a re-attach keeps the id of every stage it still has. Detach (`format_detach_season`) removes the row and its stages; a team that points at a stage blocks it (`format_detach_blocked`). A replace and a detach also empty the league's nine runtime tables (`format__clear_runtime`), and refuse first with 409 `format_runtime_has_data` when a draw, gifts, submitted picks or adjustments exist, unless `confirm_clear: true` is sent (see Format engine and runtime). Both functions are redefined in `20261105120000`, with the new `p_confirm_clear` argument and the shared check `format__guard_runtime_clear`; the old signatures are dropped, so deploy the migration before the code.

**Rule preset stages.** A stage whose ruleset is `{ kind: 'preset', preset }` has no stored ruleset yet. The attach creates one ruleset DEFINITION per distinct preset (`ensurePresetRulesets` in `src/lib/ruleset-studio/materialise.ts`, through the Ruleset Studio library): owned by the league (private, `season_id` set, so the admins of that league manage it), based on the preset with no changes, published as version 1, and the phase pins that version. The effective rules, including a roster or Little Cup allowlist, are computed by the ruleset compile at that publish. `season_formats.preset_rulesets` records preset id to definition id: a re-attach reuses the definition (pinning its current head, so the admin's edits survive), and a re-attach or detach deletes the recorded definitions nothing pins any more, in the same transaction as the stages (`format_delete_unused_preset_rulesets`); a definition held by a league in the trash is skipped. If the attach fails after the definitions were created, the caller discards them, so a failed attach leaves no orphan. Details: [Ruleset Studio](./ruleset-studio.md#interplay-with-the-format-studio-and-the-league-trash), [Ruleset Presets](./ruleset-presets.md).

**Stage materialisation** (`materialise.ts`, pure). One `tournaments` row per kit stage, in the compiled graph order (`stage_order` counts from 1):

| `tournaments` column | From the stage |
|---|---|
| `format_stage_key` | `key` |
| `name` | the stage name resolved in the league language, cut to 200 characters, `Stage <n>` when empty |
| `bracket_type` | the compiled plan's mapped bracket type: round robin and manual to `round_robin`, `swiss`, `single_elim`, `double_elim` |
| `ruleset_id` | the pinned version of the named ruleset (its head at attach time); for a rule preset stage, the head version of the ruleset the attach created or reused for that preset (below); else the league's ruleset |
| `best_of_default` | `series.best_of` |
| `bo_overrides` | the series overrides under the English round names the generators write (below) |

| `bracket_reset_enabled` | the double elimination's `bracket_reset`, else `true` |

Series overrides map to `bo_overrides` names by bracket type: round robin and Swiss count from the start (`Round N`); from the end they need an exact round count. Single elimination names the last three rounds `Finals`, `Semifinals`, `Quarterfinals` (usable without a total) and the others `Round N`. Double elimination names depend on the bracket structure, so nothing maps. When two overrides land on one name the first wins. Overrides that cannot be named are returned as warnings, not dropped silently.

**Engine gaps.** Attach returns what the league's engine does not run as `warnings`, codes with params and no text (the attach panel words them): `override_unmapped` (`stage`, `round`, `from`, `best_of`), `rr_legs_not_run`, `edge_select_not_run` (`edge`, `kind`), `groups_not_created`, `pairing_not_run`, `constraints_not_run`, `calendar_not_run`, `end_when_not_run` and `foreach_group_not_run`. On `legacy` and `shadow` all that apply are listed. On `kit` the gaps the kit closes are dropped (`engineGaps`): the legs (except for a round robin whose groups are managed by the league: see Round bounds and mirrored groups), every edge selection, the filter, bipartite and challenge pairing, group formation, the constraints, the calendar, `end_when` and `foreach_group`. What remains on `kit` is `override_unmapped`, `groups_not_created` for a `manual` group method (the admin places the players). A challenge ladder is not a gap on `kit`: players run it through the challenge routes.

**Readiness.** A custom league without an attached format cannot start. The database trigger `trg_seasons_require_attached_format` refuses a status change to `active` (`format_not_attached`, mapped by `updateSeason`) and is the backstop for every path; `POST /api/generate-round/[tid]` and `POST /api/tournaments/[id]/generate-bracket` check it first, before any round exists, and only for a custom league (the season type is already joined onto the tournament, so every other league type takes no extra read). `PATCH /api/seasons/[id]` refuses a change of `format_type` to or from `custom` while a format is attached or after the league started (`season_format_type_locked`); a change between the legacy types is untouched. On the kit engine the first round of a format with a draw or a gift form is also refused until the draw is made and missed-action checks are resolved (409 `format_not_ready`, `?force=true`, see Format engine and runtime).

**Error codes.** `format_not_found`, `format_preset_not_found`, `format_stale_revision`, `format_slug_taken`, `format_document_not_json`, `format_document_not_object`, `format_document_too_deep`, `format_document_too_many_nodes`, `format_document_too_large`, `format_document_too_large_to_store`, `format_document_name_required`, `format_publish_invalid`, `format_nothing_to_publish`, `format_not_published`, `format_published_locked`, `format_visibility_forbidden`, `format_preset_locked`, `format_attached`, `format_has_versions`, `format_version_immutable` (catalog `errors/admin`); `format_season_not_custom`, `format_season_started`, `format_attach_forbidden`, `format_attach_invalid`, `format_attach_ruleset_required`, `format_attach_manual_phases`, `format_not_attached`, `format_nothing_attached`, `format_detach_blocked`, `format_runtime_has_data`, `season_format_type_locked` (catalog `errors/seasons`); the live routes add `format_not_running`, `format_not_participant`, `format_season_closed`, `format_action_unknown`, `format_action_already_submitted`, `format_action_invalid`, `format_check_not_found`, `format_check_not_open`, `format_request_too_large` and the `format_adjust_*` family (`errors/seasons`), and `format_not_ready` (`errors/tournaments`). The status of each code is in `FORMAT_ERROR_STATUS`; the database signals map in `mapFormatDbError`.

**Known limits.** The publish, attach and detach functions are single transactions, but `generate-round` takes no league lock: a round generated in the milliseconds between the attach's started check and its stage delete needs two admins acting at once, and the function only deletes stages it proved upcoming and round-free. Draft autosave is limited to 300 saves per 10 minutes per player.

### Format engine and runtime

The engine in `src/lib/format-engine` runs the format attached to a custom league. Three migrations and one library folder carry it: `20261104090000` (`match_outcomes`), `20261104100000` (`tournaments.third_place_enabled`), `20261104100100` (engine backfill), `20261105090000` (the nine `format_*` runtime tables and their writer functions), `20261105120000` (`tournaments.format_group`, the group-forming unique index, the attach reset guard) and `20261106090000` (`format_challenges`). The pure half is client-safe and shared with the public pages; the server half (`*-server.ts`, `load.ts`, `hooks.ts`, `cron.ts`) reads and writes.

**Engines.** `season_formats.engine` is `legacy` (the classic code of the league type orders, scores and advances the phases), `shadow` (the legacy tables stay in force, the kit computes alongside for the admin diff) or `kit`. A league attached after the engine release starts on `kit`; leagues attached before it were moved to `legacy` by `20261104100100`, which also rewrites the `season_formats` rows captured in the league trash, so a restored pre-release league does not wake up on `kit`. `PUT /api/seasons/[id]/format/engine` (league admin, `format-engine` 30 per hour, body `{ engine }`, audit `season.format.engine`) switches it at any time, also after the start: it changes how the next round pairs and how tables rank, never a stored result; a re-attach keeps the engine the admin chose. `GET /api/seasons/[id]/format/shadow` (league admin, `format-shadow` 60 per hour) lists, for every phase and for the season table, the rows whose place or points differ between the legacy and the kit table, on every engine (a `legacy` league sees what switching would change). It costs the kit reads, so no public page calls it. `isKitCandidate(tournament)` (`kit-candidate.ts`, types only) is the question every hook asks first: a phase of a `custom` league. Anything else does nothing and imports nothing.

**Standings** (`standings.ts`, `context.ts`, `load.ts`; pure and client-safe). A stage's table comes from its completed matches, their `match_outcomes` rows, the stage's `scoring` and its `rank` chain; the same function serves the public table, the pairing, the advancement and the runtime, so they cannot disagree. An `unresolved` outcome is never scored; a `forfeit` or `no_show` scores the stage's forfeit points when it has them, else win and loss; a played match scores win or loss plus `per_opponent_faint` times the opponent's fainted Pokémon, read from the outcome row only (never from `battle_stats` at read time). Byes score only in a Swiss stage, as in the public table. Builtin metrics: `points`, `wins`, `losses`, `games_played`, `kill_differential`, `buchholz`, `faints_dealt`, `faints_taken`, `seed` (`tournament_participants.seed` of the phase) and `rating` (`player_ratings.rating`, global); the loaders read the last two only for a stage that ranks by or shows them, and a player without a row sorts last (`seed`) or reads 0 (`rating`). Custom metrics (`metric.define` of players and `score.placement` tables) and the point and rank adjustments of admins ride along as `StageTableExtras` (`loadStageTableExtras`), so advancement, pairing and the runtime rank the way the public page does; a `foreach_group` stage runs one phase per group, and an adjustment goes to the player's group phase. Rank steps: `metric`, `head_to_head` (`pairwise` or `mini_table`), `coin_flip` (from the season seed; the public data carries the precomputed draws, never the seed), `decision_match` (a flag: the rows stay tied and a `standings_tie` check can open) and `manual` (the admin's order of a `rank` adjustment). `rel()` inside a metric answers from the links the public may see whole (`publicLinkPairs`), so a hidden side never reaches a table. The golden-parity tests hold every fixture league's described stages to the legacy tables for seeded results, forfeits and faint tallies.

**Pairing** (`pairing.ts`, `pairing-server.ts`, `groups.ts`). Swiss pairs by the stage's own table (`rounds` caps the stage, `auto` is `ceil(log2 n)`; with `avoid_repeats` off earlier pairings do not steer the search and the round reports its rematches); round robin plays `legs` circle schedules (a later leg swaps sides; with `mirror_legs` off every second leg also runs backwards); a grouped round robin pairs each group's own circle. `manual` is paired by an admin in the manual round editor; the elimination brackets are built whole by the bracket engine. **Filter** wraps Swiss or round robin and never pairs a pair its `allow` expression rejects (a pair is allowed when the expression holds for at least one order of the two players; Swiss takes the pairing with the fewest rejected pairs when none is clean, a round robin drops the rejected pairs); a round that had to break the filter opens a `pairing_forbidden` check (`forbidden:<stage>:<round>`), and an `allow` that cannot be evaluated is a 422 instead of a guess. **Bipartite** splits the players by an enum attribute into side A and side B and plays the pre-generated A x B schedule: a cyclic Latin rectangle built from the two sides in seed order (round `r`: the `i`-th player of the smaller side meets the `(i + r) mod m`-th of the larger side, `m` being the larger side), so every A meets every B exactly once over `max(|A|, |B|)` rounds whatever the standings do; the surplus of the larger side sits out. A pair that already played moves the round to the next schedule round; only when every meeting has happened does the standings-based search take over, and its extra meetings are reported as rematches. A player on neither side plays no round. The compiler warns (`bipartite_rounds_short`) when `rounds` is below the larger side's size, but only when the sides are knowable: the attribute is assigned to every player (`random_seeded` or an expression, not by hand), `side_a` and `side_b` name every value of it, and the plan knows the stage's (or one group's) player count. **Challenge** ladders have no generator: see Live format routes. Making a challenge also cancels the phase's open challenges of players who have left the phase (they would count against `max_open`); removing a player does not cancel their challenges at once (a trigger on the enrollment would also fire on the sync, which replaces the roster by deleting and re-inserting it), but an acceptance rechecks the enrollment. **Groups** (`group.form`): `formKitGroups` forms a stage's groups from its enrolled players before the first round by the spec's method (a `manual` spec forms none); league groups win, and a phase that already has groups or rounds keeps them. Two first-round generations of one phase can race: `uq_tournament_groups_tournament_group_number` (`20261105120000`) stops the second insert and the loser answers 409 `groups_forming_in_progress`.

**Advancement** (`advancement.ts`, `advance.ts`, `auto-advance.ts`). An edge's selections run in order and never pick a player twice: `top_n`, `per_group`, `wildcard` (the best of those not yet picked), `threshold` (the expression sees `points`, `wins`, `losses`, `games_played`, `rank`, `group_rank`, `faints_dealt`, `faints_taken`, `kill_differential`, `buchholz`, `participants` and the `standings` collection), `bottom_n` and `manual_list` (the edge waits for the admin's list). Seeding of the target: `rank`, `cross_group` (every group's first, then every group's second), `random` (season seed) or `manual`. An edge with gate `auto` advances its players into the target phase when the source phase completes, as if an admin had pressed Advance; it is best effort (a failed target is logged and audited, the others still advance, and the Advance button remains), an `admin_confirm` edge waits. `Stage.end_when` (`rounds` or an expression over `round`, `rounds_played`, `open_matches`, `participants`, `tunable.*`) completes the phase through the same sequence as the admin's status change (`completePhaseAtStageEnd`), evaluated when the last open match of a round completes. A match counts as open until its own `match_completed` event has fired (not only until its status is `completed`), so the phase never ends while a sibling's completion effects are missing; the sibling's hook, or the heal's re-run of it, evaluates `end_when` again. A reaction that fails after the phase flipped (the `stage_end` event, the tie checks) fails the hook step too, and the heal's re-run repeats just that reaction on the completed phase (idempotent by event and check keys). A stage that repeats per group ends with its last group phase.

**Runtime state** (`runtime/state.ts`, `runtime/load.ts`). `loadFreshKitContext(seasonId)` reads the attached format (spec, season seed, tunables, amendments), the phases and the nine `format_*` tables into one `KitRuntimeState`; `loadKitContext` is its per-request memo for pages that only read, a writer always takes the fresh one. The seed is server side only. The tables, all service-role only, owned by the league (recycle bin) and cleared by `format__clear_runtime` on a replace or detach: `format_relation_links`, `format_resource_items` (an `exclusive` item is unique per league by a partial index), `format_action_submissions`, `format_event_log` (one row per event key with the ops it applied), `format_flags` (`domain:<key>` locked or unlocked, `action:<key>` open or locked), `format_player_attrs`, `format_track_progress` (only ever raised), `format_checks` (unique `(season_id, dedupe_key)`; sources `unresolved_outcome`, `standings_tie`, `pairing_rematch`, `pairing_forbidden`, `deadline_missed`, `team_audit`, `expr`), `format_adjustments` (kinds `points`, `resource`, `relation`, `outcome`, `action`, `domain`, `rank`; a reason of 1 to 500 characters is required) and, from `20261106090000`, `format_challenges`. Every write is one SQL function in one transaction (`format_fire_event`, `format_action_save`, `format_action_submit`, `format_apply_adjustment`, `format_check_open`, `format_check_resolve(season, check, ...)`, `format_challenge_create/respond/cancel/expire`); a failing op rolls the whole call back. No function is `SECURITY DEFINER`, all set `search_path`, all are granted to `service_role` only. `format_check_resolve`, `format_challenge_cancel` and `format_challenge_respond` take the league id and filter on it, so an id of another league resolves nothing. Save, submit and the `lock_action` op of one action run under one advisory lock (`format__lock_action`), so a submit cannot slip in after the lock.

**Events and effects** (`events.ts`, `effects.ts`, `fire.ts`). A `KitEvent` is `stage_start`, `stage_end`, `round_start`, `round_end`, `match_completed`, `action_locked` or `time`; its key makes firing idempotent per league: `stage_start:<stage>`, `round_start:<stage>:<round>`, `match_completed:<match id>[:<n>]`, `action_locked:<action>` and `time:<stage>:<mark>`. The stage is part of a time key because a mark key is unique only within its stage's calendar; a rule's `on: { event: 'time', mark }` names the mark only and reacts to the mark of every stage that has it. `planEffects` walks the format in a fixed order (every `rule.on_event` whose trigger and `when` hold, then every relation whose `reveal_on` matches, then every action whose window opens or closes on the event) and returns ops, notifications and skipped problems; **a `notify` effect is planned and returned in the fire result and nothing more: it is not stored and no player or admin receives it (no play-page notice, push, Discord post or email consumes `FireResult.notifications` yet), so the rule text of a format must not promise that anyone is told; a grant never exceeds a resource's capacity (an exclusive grant is skipped when somebody holds the item) and is reported, not fatal. `fireEvent` applies the ops in `format_fire_event` and then expires the public reads. A `lock_action` op fires `action_locked` itself (up to three levels deep) in a second transaction, which can be lost, so `fireLockedActionEvents` fires the event for every action whose flag is `locked` and whose event has not fired, on a retry of a fired event and in every cron pass; a manual lock through an adjustment fires it the same way. **Expression scoping.** `rand('key')` draws from (season seed, scope, key) and its key is a literal, so evaluations that share a scope draw alike. The scope names the subject where there is one (the player in the player, match and team env, the entry in the entry env, the sorted pair in the pair env, `metric:<stage>:<player>` for a metric), so each subject gets its own draw from the same expression and the draw never changes between evaluations. An env without a subject (event, stage) has one draw per event or stage. The seeded draws of the engine itself (coin flip, group method, relation draw, deadline picks) use their own scopes.

**Player actions** (`actions.ts`, `actions-server.ts`, `random-pick.ts`). A `player.action` is a form of 1 to 8 steps: each step picks `count` entries of a domain into a resource of the target (the `to` side of the actor's link in `via`, or the actor for a self action). `validateActionSubmission` reports every problem, not the first (`window_closed`, `domain_locked`, `item_outside_domain`, `distinct_attr`, `exceeds_capacity`, `resource_item_taken`, ...). Window: the flag `action:<id>` is `locked`, `open` or absent, in which case the action is open unless its `opens_on` event has not fired; an admin opens or locks by hand with an `action` adjustment. A player picks only from what the player may see (`audience: 'player'`): an `admins` domain, or a `when_unlocked` domain that is still locked, is a hidden pool: a player's submission against it is answered with `domain_locked` alone (a step-level issue without an `item_id`) and no per-pick check runs, so a refusal can never tell a member id from a non-member (`wrong_count` still applies, because it reveals only how many picks were sent). A public locked domain keeps the per-pick answers, because its entries are public. The cron's deadline pick uses `audience: 'system'` and keeps every per-pick check. The database re-checks the races a read cannot close: `action_locked`, `resource_item_taken`, `resource_capacity_reached` and `format_context_stale`. **Format revision.** `season_formats.revision` takes a new number from one sequence on every insert and update of the row (attach, replace, engine switch, domain amendment), so a detach and a new attach never reuse one. `loadFreshKitContext` reads it together with the spec (`KitContext.revision`) and `saveAction` / `submitAction` hand it to `format_action_save` / `format_action_submit` (`p_expected_revision`), which compare it under the action's advisory lock after taking the `seasons` row `FOR KEY SHARE` and the `season_formats` row `FOR SHARE`: an attach, a detach, an engine switch or an amendment either committed before (the write is refused as `format_context_stale`, 409, nothing written, and the player view reloads) or waits for the write. The cron's deadline draw carries it too and skips the player until the next pass. `format_fire_event` and `format_apply_adjustment` take `p_expected_revision` as well: the events and adjustments are planned against the spec the library loaded, so a plan made for another version is refused with `format_context_stale` (409) BEFORE the event key is logged (nothing is recorded, the event can be fired again against the fresh format). The cron and the hooks treat it as retry-later (a warning, not an error: the next cron pass fires the event again, `fireLockedActionEvents` included); an admin adjustment that hits it is answered 409 and not saved, and a manual lock whose follow-up `action_locked` event comes back stale still logs at error level in `adjust.ts` (the cron retries it). The check reads the `season_formats` row `FOR SHARE` (`format__check_revision`), or `FOR UPDATE` where the adjustment writes the row itself (`format__check_revision_for_update`, a domain amendment). **Capacity.** The capacity of a resource is read from the attached spec inside `format__insert_item`, under the per-(league, resource, player) advisory lock `format__lock_holding` that every grant takes (a submit, an event's `grant_item` and an adjustment's), so two grants of different actions or paths cannot both take the last free unit: the loser raises `resource_capacity_reached` (409) and its whole call rolls back (the TS checks only decide earlier and with a friendlier answer). An admin resource adjustment is capped as well. **Lock order**, for every writer (submits, events and adjustments alike): relation, action, the revision rows, holding, each sorted. The relation and action locks of an op batch are taken by `format__lock_op_keys`, called by `format__apply_ops` and by `format_fire_event` / `format_apply_adjustment` before the revision check, so an event that locks an action cannot deadlock with a domain amendment (which holds the action locks and then wants the `season_formats` row). **Save and submit.** `PUT .../actions/[actionId]` saves a draft; `POST .../submit` submits and claims the exclusive items atomically (a second submit replaces the row and the items it granted). The route refuses to save over an already submitted pick (409 `format_action_already_submitted`: the player submits again to change it), but the SQL function itself demotes: a save that reaches the database over a `submitted` row (the race between the route's read and the call) turns it back into a `draft`, deletes the items the submission granted and clears `submitted_at`, so a draft never keeps exclusive items, the lock skips it and a deadline policy treats the player as not having submitted. A `seeded_random_pick` is made only for a player without a submission: the cron checks a fresh read, and the submit itself passes `p_only_if_unsubmitted`, so `format_action_submit` raises `action_already_submitted` (under the action's advisory lock) instead of replacing a pick the player submitted in between, and the cron then skips that player without a count or an audit entry. The cron records each one as `season.format.action.auto_pick` (System actor, `metadata.via` `seeded_random_pick`), naming no player while a relation still hides the giver.

**Checks** (`checks.ts`, `checks-server.ts`, `pairing-checks.ts`, `deadline-policy.ts`, `team-audit.ts`). A check is a situation an admin should look at; it records the admin's verdict (`confirmed` or `rejected` with a note) and has no effect on the engine, the consequence being the existing adjustment surface. Dedupe keys: `unresolved:<match>:<generation>`, `tie:<stage>:<sorted player ids>` (stage completed, rank chain ending in a decision match), `rematch:<stage>:<round>`, `expr:<rule>:<player>` and `expr:<rule>:<match>:<generation>`, `forbidden:<stage>:<round>`, `deadline:<stage>:<policy index>:<match or action:player>` and `team_audit:<match>:<generation>:<player>`. The first four come from `check.assisted` rules; the pairing, deadline and team-audit checks need no rule in the format. The per-match checks (`unresolved`, match-level `expr`, `team_audit`) carry the completion generation of the match (`match_reverted:<match>:*` events fired so far), so a result that is reverted (reset, reopened, a game deleted or edited) or a dispute that is reopened closes the still-open checks of the old generation as rejected (`note` `match_reset`) and advances the generation: the next completion or tie opens its own checks instead of hitting a decided key. When one of those checks cannot be closed, the revert event does not fire (the call reports failure and the format cron's revert heal tries again), so the generation never moves past an open check.

**Adjustments** (`adjust.ts`, `adjustments.ts`). `adjust.manual` lists the kinds a format allows; each adjustment is one `format_apply_adjustment` call (the audit row and the ops commit together, against the format revision the library loaded: a format that changed in between answers `format_context_stale`, see Format revision) and needs a reason. `points`: the row itself is the effect (at most 1000, two decimals). `rank`: the admin's whole order of a stage, a permutation of its roster (`invalid_order`). `resource`: a positive amount grants, a negative one revokes; a domain resource needs an item that is an entry of the domain as amended (`item_outside_domain`) and names one (`item_required`), a counter takes none (`item_not_allowed`), and a revoke needs the units to be held (`insufficient_holding`). The two refusals that read state (`relation_has_links`, `insufficient_holding`) are decided twice: against the context the library loaded, and again inside `format_apply_adjustment` under a transaction advisory lock (the function raises, the history row rolls back with it, and the library answers the same issue), so two overlapping requests cannot both be recorded when only one changed anything. The history (`GET .../adjustments`) holds to the player-visibility rule for an admin who also plays: a resource adjustment of another player on a resource that is not `visibility: all` shows its kind and reason only (no resource, player, item or amount), and the audit entry never carries the item. `relation`: `reveal`, `links` while the relation has none (an existing link is never edited: `relation_has_links`; links must fit the roster and the shape: `invalid_links`), or `draw`, which sets the links from the season seed and the league roster (the seed never leaves the server; `draw` and `links` exclude each other), and the history row keeps only the number of links, never a pair. `action`: open or lock by hand; a state the action is already in is refused (`action_state_unchanged`, 409), so the history never records a lock or an opening that did not happen, and `open` flips the action's flag only (a submission that was already locked stays locked). `domain`: an amendment (`add`, `remove`) appended to `season_formats.amendments`, refused while an action using the domain is locked (`domain_amendment_locked`), after at most 64 amendments (`amendment_limit`), and never for an attribute the action's `distinct_attr` needs (`attr_missing`). `outcome` is record-only in the library and not exposed by the routes.

**Calendar, deadlines and the cron.** `Stage.calendar` turns rounds into instants: round `n` opens at the wall time `time` on the day `start + (n - 1) * every` (weekly or daily cadence) in the league's time zone and closes `round_window_hours` of elapsed time later; a mark fires `offset_hours` after the opening of its round. Policies (`calendar.deadlines`): `match` and `team` on a round past its instant act on each match still `scheduled` or `in_progress` (`forfeit` settles it when exactly one side has no registered team, the match-linked row else the planned one, like the team audit reads it; else a `deadline_missed` check opens, as it does for `admin_review`); `action` policies `auto_lock`, `admin_review` (a check per player who has not submitted) and `seeded_random_pick` (a pick drawn from the season seed; a check when none is valid) also run for an `upcoming` phase, which is how a gift form before round 1 closes. The compiler refuses a random pick that could never be made (`deadline_policy_invalid`, reason `pick_after_close`: the pick is due at or after the action's closing mark or round, so the offset has to be negative). `GET /api/cron/format-engine` (every 15 minutes, `CRON_SECRET`, `maxDuration` 300) runs `runFormatCronPass`: it fires due marks and applies policies, expires challenges, fires lost `action_locked` events and backfills `match_completed` for finalized matches whose event never fired (this sweep covers every running kit league, calendar or not, and also leagues that were not on the kit engine when their matches finished: a league switched from `shadow` or attached late has its history applied retroactively, including track progress, event effects and expression checks; this is a property of the switch, not an option, and a long history takes several runs because of the limits below. A match that was completed before `match_outcomes` existed has no outcome row and scores as `played` with 0 faints, so its per-faint points are 0). A run handles at most `FORMAT_CRON_LEAGUE_LIMIT` (100) leagues in a window that moves on once per 15-minute slot (`cronWindowStart`, so with more leagues than one run handles every league is reached within a few runs), stops starting leagues after `FORMAT_CRON_BUDGET_MS` (240 s), and takes at most `FORMAT_CRON_BACKFILL_LIMIT` (25) backfills per run and 10 per league. **Pending reverts are retried** (`healPendingReverts`): a match whose current `match_completed` key is fired but which is no longer completed (a reset or reopen whose revert failed) is reverted again, scanning `FORMAT_CRON_REVERT_SCAN_LIMIT` (500) matches per league and run in a window that moves with the slot, at most `FORMAT_CRON_REVERT_PER_LEAGUE` (10) per league and `FORMAT_CRON_REVERT_LIMIT` (25) per run; each match is re-read right before the revert and skipped when it completed again, and a failed revert is logged, counted in `failures` and retried by the next run. The heal also visits the completed and archived kit leagues (`listKitIdleSeasonIds`), where an admin can still reopen a match, but nothing else runs there (no phase, deadline, lock repair or backfill): after the running leagues, in a window of `FORMAT_CRON_IDLE_LEAGUE_LIMIT` (10) leagues per run that moves with the slot, within the same revert and time budgets, and scanning every currently-completed match of such a league (a chunked indexed read; a slot-keyed scan window would alias with the visit pattern of a league that is only visited every few slots); with `N` such leagues a failed revert there can wait up to `ceil(N / 10)` runs for its turn. Two limits stay: a match completed again before the retry finds the old key fired, so the new completion applied nothing and the old winner's effects stand (the trace is the logged failed revert), and a hard-deleted match row cannot be reverted from here. The team audit has one residual gap: when the audit never ran and opening its `audit_unavailable` check fails in both backfill calls, only the log and the run's failure count remain (see the module header of `team-audit-server.ts`). One league's failure is logged with its original error and counted; the run then answers 500 `format_cron_partial_failure`. The summary counts `leagues`, `deferred`, `marks`, `forfeits`, `checks`, `locks`, `picks`, `completions_backfilled`, `challenges_expired` and `failures`.

**Match hooks** (`hooks.ts`). All best effort except the completion: `onRoundGenerated` (`stage_start`, `round_start`, a rematch check), `onPhaseStatusChanged` (`stage_start` on `upcoming` to `active`; `stage_end` plus the tie and expression checks on `completed`), `onMatchUnresolved` (the `unresolved_outcome` checks) and `onMatchCompleted`, which the match finalize awaits as its `format_hook` step ([Match](./match.md#match-finalization)). A completed match fires `match_completed` with the track progress of both players in one transaction, opens the expression checks, runs the team audit and then evaluates `end_when`. A result that is reset and played again is a new completion: `onMatchReverted` takes back the revocable ops of the old event (a granted item is revoked, awarded points are cancelled with a negative adjustment) and logs `match_reverted:<match>:<n>`; the n-th completion's key is `match_completed:<match>` for n = 0 and `match_completed:<match>:<n>` after, where n counts the reverts. `completionGeneration` (hooks) and `currentCompletionKeyOf` (events.ts, used by `currentlyCompletedMatchIds` in cron.ts) both implement this count and must stay in step.

**Team rules** (`team.ts`, `team-server.ts`, `team-audit.ts`, `team-audit-server.ts`, `src/lib/team/kit-team-gate.ts`). `Stage.constraints` are evaluated against one team (`roster_size`, `count`, `distinct`, `type_quota`, `tera`, `evolution_stage`; `when` is evaluated in the team env, so a rule can follow the round). A source matches a team member by its species id or its base species. **Team rules are advisory plus a post-match audit (not a gate).** `POST /api/teams`, `PATCH /api/teams/[id]` and `POST /api/match-prep` never refuse a team for the stage rules; the success body may carry `team_check` for the team's own player only (a site admin saving another player's team gets none: the verdict reads that player's private gifts and pools) (absent: no kit rules or rules met; `{ status: 'unmet', verdict }`: the full `TeamValidationResult`, worded by the client from its codes; `{ status: 'unavailable' }`: the verdict could not be computed, logged with the original error and never reported as "meets the rules"). `adviseKitTeam` never throws, and `team_check_failed` (the old 400) no longer exists. A match-bound team is judged at its match's round; a team checked outside a match uses `min(latest generated round, calendar round)` when the stage has a calendar (`currentPhaseRound`). `POST /api/validate-team` is unchanged except for an optional `match_id` (needs `tournament_id`, wins over `round_number`; 404 `match_not_found`, 403 `match_prep_not_participant`, an admin who is not in the match gets the ruleset verdict only) and a rate limit of 240 per minute and player. The coverage badge of a team constraint is Checked, not Auto: nothing refuses a team, an admin confirms the audit's result.

The **audit** runs after every completed match of a kit league (from `onMatchCompleted`, before the stage can end). It audits the stage's constraints only, on the team the match was played with: the registered team (the match-linked row, else the planned one) is evaluated at the match's round, with the state before this completion's own effects (so a heal run sees the same state), and the species of the Pokémon the replay shows were brought are cross-checked against it. A side that breaks the rules, differs from the replay, has no registered team although it played, or could not be audited opens a `team_audit` check, key `team_audit:<match>:<completion generation>:<player>`; reasons `rules`, `observed_mismatch`, `no_registered_team` and `audit_unavailable` (causes `ruleset_missing`, `team_rows_duplicate`, `read_failed`). The subject holds codes, ids and counts only and is **admin-only**: planned teams stay hidden under `team_visibility`, so only an admin route may read it. A permanent cause opens `audit_unavailable` instead of failing the hook; a transient failure retries only inside `AUDIT_RETRY_WINDOW_MS` (24 hours), so an audit can never wedge a match. A reset closes the still-open audit checks of that completion (rejected with the note `match_reset`). Limits: only the registered team is audited and only the species of the brought Pokémon can be cross-checked (items, Tera types and moves are unobservable). The species match is by forme: a played Rotom-Heat is off a team that registered Rotom-Frost (different pools may split formes of one dex base), while a battle forme of a registered species (Mimikyu-Busted, Greninja-Ash), any forme of a registered base-forme Pokémon (an item picks Ogerpon's or Arceus's forme) and a bare base name (a hidden preview does not show the forme) all count as covered; a same-species edit of items, Tera or moves after the replay was submitted is visible only as `edited_after_play` evidence; breaks of the phase's RULESET (banned species, moves, size) are advisory only and not audited, as in the classic leagues; flags and later-round grants are not time-travelled (an audit evaluates the state of today, with `evaluated_at` recorded), so a format should express round-dependent legality with `when` on `round`, never with a lock flag; there is no severity on a constraint (every one is advised and audited).

**First round and re-attach guards.** The first round of a kit phase is refused with 409 `format_not_ready` (`params.reasons`, comma-separated: `relation_undrawn` when a relation an action runs `via` has no link while the league has two or more players, or has links but leaves an enrolled player out of every one (enrolled after the draw; links can not be redone), `action_incomplete` when a `deadline_missed` check of an action policy is still open) unless the caller passes `?force=true` (the round manager offers it as a "Start anyway?" confirmation after the 409); the override is audited as `season.format.round.force_start` with the reasons it overrode, written once the round exists (`announceKitRound`), not by the guard, so a request that is still refused afterwards (too few players, groups forming, a pairing error) leaves no entry. A relation that a `generate_relation` effect of a rule on `stage_start` (when the round starts the phase and the event has not fired) or on `round_start` of round 1 draws right after the round is written does not count as undrawn: that draw runs over the same roster before anything is played. A format with no `via` action and no action policy never reports anything. The readiness card gains a `calendar_start` item (a stage calendar needs a start date, and marks already past are listed until the league starts; the input has no event log, so it cannot tell a mark that already fired from one the next cron pass will fire and keeps listing a due mark until the league starts). A replace or detach over relation links, resource items, submitted picks or adjustments is refused with 409 `format_runtime_has_data` (`params` `{ links, items, submissions, adjustments }`) unless the request carries `confirm_clear: true` (`POST` body, `DELETE` optional JSON body); a first attach and a league without such rows are unaffected, and the clear (`format__clear_runtime`) empties the nine runtime tables because their event keys, flags and picks belong to the spec that is going away. The count and the clear are two statements under the league's lock; a gift committed by another transaction in between would be deleted uncounted (a window of milliseconds while the admin is re-attaching).

**Round bounds and mirrored groups** (`route-guards.ts`: `batchRoundCap`, `assertBatchMayRunAhead`, `assertMirroredGroupsPlayLegs`). A stage whose `end_when` is `{ kind: 'rounds' }` caps `generate-all-rounds`: the batch writes no round past the bound. A stage whose `end_when` is an expression is checked after every round and can end the phase early, which would strand rounds already written ahead of it, so a batch of two or more rounds is refused with 409 `rounds_batch_end_when_expression` and the rounds are generated one at a time with `generate-round` (a batch of one is the same as that and passes; the round manager can offer the round-by-round path on this code). A kit round robin with more than one leg whose groups mirror league groups (every group carries a `season_group_id`) is refused with 409 `rounds_mirrored_groups_legs` (`params.legs`) by both `generate-round` and `generate-all-rounds`: those groups follow the league week plan (cross-group weeks, placement weeks), a single schedule with no legs or side swap, so the configured legs would be dropped without a word. League groups always win over a stage's own groups, so the way out is to use a single leg or to remove the league groups (a stage cannot form its own groups while the league has any); the refusal comes at generate time, not at attach or amend time. The legs are played by a stage in a league without groups, or with a single leg; this is why the legs gap of Engine gaps is not closed for league-managed groups. The hand-paired route `rounds/manual` is not affected.

**Diagnostics of the runtime sections.** The compiler reports 100 codes in all (59 before Phase 3). The 41 added since cover the Phase 3 and 4 sections: expression and reference checks (`ref_unknown`, `expr_invalid`), attributes (`attr_values_required`, `attr_values_unexpected`, `attr_value_duplicate`, `attr_multi_invalid`, `attr_assign_on_entry`, `attr_random_type`), domains (`domain_entry_duplicate`, `domain_entry_unknown_species`, `domain_attr_unknown`, `domain_attr_duplicate`, `domain_attr_value_invalid`), relations and resources (`relation_roster_too_small`, `resource_exclusive_needs_domain`), metrics and tunables (`metric_key_builtin`, `tunable_values_mismatch`, `tunable_bounds_invalid`, `tunable_default_invalid`), effects and actions (`effect_item_invalid`, `effect_set_attr_invalid`, `action_step_mismatch`, `action_distinct_attr_invalid`, `action_distinct_attr_missing`, `action_exceeds_capacity`, `action_close_missing`, `adjust_kind_duplicate`), pairings (`bipartite_attr_invalid`, `bipartite_value_invalid`, `bipartite_sides_overlap`, `bipartite_rounds_short`), constraints (`constraint_bounds_invalid`, `constraint_attr_invalid`, `constraint_attr_usage`, `constraint_type_invalid`, `constraint_source_invalid`, `constraint_source_hidden_domain`, `constraint_species_unknown`), calendars and stage fields (`calendar_invalid`, `deadline_policy_invalid`, `foreach_group_invalid`). Warnings among them: `relation_roster_too_small`, `action_exceeds_capacity`, `action_close_missing`, `bipartite_rounds_short` and `constraint_species_unknown`; the rest are errors. `constraint_source_hidden_domain` (params `stage`, `constraint`, `domain`) refuses a count source of kind `domain` whose domain has visibility `admins` (also inside `any_of` and `not`, at any depth) and a `distinct by attr` rule when an `admins` domain has entries carrying that attribute, because the rule would let a player read the hidden pool through a verdict; a `resource` source is allowed, because it reflects only the player's own holdings. A stored draft or fork that does this now reports an error and does not compile (no shipped example is affected). `action_distinct_attr_missing` makes a fork whose action asks for distinct values over a domain whose entries lack the attribute fail to compile, so a stored draft with such entries now reports an error. Their sentences are in `format-studio` in both languages.

### Live format routes

Under `src/app/api/seasons/[id]/format/`. Every write reads its body in the order guard, `rejectInvalidPathId` for a uuid and `keySchema` for an action key, `assertSeasonOpenForPlay` (player writes), rate limit, bounded body (8 KiB; 256 KiB for an adjustment), strict zod (an unknown member such as an `actor_id` is a 400), library call, audit (`logAuditEvent`, not awaited). Season-scoped everywhere: the league comes from the URL, a challenge or check id of another league is `*_not_found`, and the actor of a player route is always the session player. Reads answer `Cache-Control: private, no-store`. Player writes are refused in a completed or archived league (409 `format_season_closed`); the reads and the admin routes stay open there so history can be corrected. A reason longer than 500 characters is a 400 `validation_failed` at the route.

**Privacy contract** (`runtime/views.ts`, the only place that builds these answers). Every DTO is built by copying named fields: a raw row of `format_action_submissions`, `format_resource_items` or `format_relation_links` never reaches a response (a submission row carries `target_player_id`, an item row `source` and `source_ref`). Relations go through `visibleLinks`, which sorts by the visible fields only (never by the hidden side), so a hidden side is `null` and cannot be recovered by position; the admin overview is masked like a player's (the admin may also play) and only the audited unmask shows hidden sides. Domain entries go through `visibleEntries`: an `admins` domain and a locked `when_unlocked` domain ship no entries. Another player's items are shown only for a resource with `visibility: 'all'`. The `taken` flag is different: it is sent on the pickable entries of an action step for any **globally exclusive** resource, whatever its visibility, as `{ id, reason: 'taken' }` with no holder and no moment (items and holders still follow the resource's visibility, so a secret resource yields the flag and empty items). Admins pools and still-locked pools ship no entries and therefore no flag, a non-exclusive resource gets none, and the viewer's own current pick (the submission being replaced) is never flagged. This supersedes the design notes that said `taken` only for visibility `all`. A viewer sees only their own submission and challenges. No DTO has a member called `status` (a `players` column; states are `state`). A player who is not a current participant is `{ id, name: null }`, shown as "former player". A check's `subject` (team audit, deadline) is admin-only and appears only in the checks list. The audit log never holds a pair, an entry list or a pick.

### Wichtelcup example

The fourth shipped example (`presets/wichtelcup.ts`, id `wichtelcup`) is a Secret Santa cup, written entirely with kit primitives: nothing in the engine knows the word. Four weekly Swiss rounds (`stage cup`, 30 points per win, 10 per loss, 1 per fainted opposing Pokémon, 30/0 for a forfeit, ties settled by a decision match). Before round 1 every player gifts two **junk** Pokémon (different primary roles) and one **premium** Pokémon to the recipient they were drawn for; what a player may bring each week then follows from their own gifts.

| Rule of the cup | Primitive |
|---|---|
| normal (64), junk (30), premium (23) and New Year (24) pools | four `domain.define`; the New Year pool starts `locked`; junk entries carry the `primary_role` entry attribute |
| Secret Santa, giver hidden until week 4 | `relation.define` `santa` (`derangement`, default visibility, `reveal_on` the `week4` calendar mark); the organizer draws it with a relation adjustment |
| gifts held by the recipient | `resource.define` `junk_gifts` (capacity 2) and `premium_gift` (capacity 1, `exclusive: global`) |
| gift form: junk first, then premium, review, lock on submit | one `player.action` `choose_gifts` (`via: santa`, two steps, `distinct_attr: primary_role` on the junk step), its window opened and closed by the calendar marks `gifts_open` (14 days before round 1) and `gifts_close` (12 hours before) |
| weekly obligations (week 1: one junk; weeks 2-3: both junk; premium from week 3; at most two New Year Pokémon in week 4) | `constraint.count` rules gated by `when` on `round` (inequalities, so a tiebreak round follows week 4) |
| only the normal pool, your OWN gifts and the New Year pool | one `constraint.count` allowlist, `not(any_of(...))` with `max: 0`; the team check reports each offender as `kit_not_allowed` on its slot |
| exactly six Pokémon, no Terastallization | `constraint.roster_size` 6 to 6 and `constraint.tera` `banned` |
| New Year pool opens and the Secret Santas are revealed in week 4 | the `week4` mark: a `rule.on_event` unlocks the domain and the relation's `reveal_on` fires, both from the calendar and not from an admin generating round 4 |
| missed gift form, team or match | calendar deadline policies: the gift action, the team (24 hours before the round closes) and the match all `admin_review`, so a missed obligation opens a check instead of a silent forfeit |

**Running it** (chosen for this release: per-player pools enforced by the team check, advisory plus audit like every kit rule). The organizer forks the example, attaches it to a custom league and confirms the primary role of every junk species. The example's two `notify` rules (`gifts_open_note`, `week4_unlock`) are planned only and reach nobody yet (see Events and effects), so the organizer announces the opening of the gift form and the start of week 4 outside the app; the rules text itself promises no notification. The gift window opens and closes by the calendar marks (the action's deadline policy and the cron also run for the `upcoming` phase, which is how the form closes before round 1). The Secret Santa is **drawn by the organizer**, an explicit confirmed action (a relation adjustment with `draw: true` and a reason; the links come from the season seed and the league roster, never leave the server and appear nowhere in the audit log); a draw cannot be redone once links exist, so the draw dialog lists the roster with its count (the same `rosterOf` the server draws over), asks for that count to be typed back and for a reason (a late enrolment that is missing is noticed before it is left without a giver and a recipient), and a re-attach that would wipe a draw or gifts needs `confirm_clear`. Round 1 is refused (409 `format_not_ready`) until the draw is made and missed-gift checks are resolved; an admin may force it, audited. Players fill the gift form on the play page, pick junk first, then the globally exclusive premium gift (a species already taken is shown as taken and refused on submit; first come, first served, and the form never says who holds it), review and submit; the recipient sees what they received. **The locked action card shows the giver's own stored picks ("Your pick"), not what the recipient holds now**: an admin resource adjustment (a revoke or a re-grant after a dropout) changes the recipient's holdings and the team check, but never the giver's card, so after such an adjustment the card can differ from the real holdings. The team check, the builder and the post-match audit read the player's own gifts, the normal pool and the New Year pool as the week allows, so the same verdict shows in the teambuilder, in match preparation and in the audit that opens a `team_audit` check for an admin to rule on. What the cup's written rules leave open is the organizer's call: the penalty for a confirmed illegal team (a check records the verdict only; the consequence is a manual adjustment or a forfeit settled through the match routes).

**Defaults taken where the design left a question open** (change them in the forked document or by an adjustment): the New Year pool is public but locked until week 4; the normal pool is shared by all players; the allowlist is by exact species id (cosmetic formes such as Alcremie flavors are not accepted unless listed); premium species taken by others are flagged as taken in the gift form (the flag exists for any globally exclusive resource, whatever its visibility), never by whom or when; because the flag follows the live state, a player who watches the form over time can still infer when a species was reserved, an accepted side channel; a missed gift deadline and a missed match deadline open `admin_review` checks (the team deadline too, at 24 hours before the close); the draw is a single cycle (nobody gifts the player who gifts them, 9! outcomes for ten players) and the rules text says so; the revealed mapping is public to every viewer, non-participants included; the ruleset layer (banned items, illegal formes, abilities) is advisory in the builder and not part of the post-match audit; a league admin may force the first round despite an undrawn Secret Santa or open missing-gift checks. A substituted player keeps their links and items and the substitute has none; dropouts and re-grants are handled by adjustment.

Legality is expressed with `when` on `round`, never with the unlock flag of a domain, so a late audit of a week-1 team does not see the New Year pool as open. The species allowlist by exact forme, the item and ability bans, the Species and Item Clause and the Silvester levels stay in the pinned rule preset `gen9natdexwichtelcup` (`stage.ruleset`), see [Ruleset Presets](./ruleset-presets.md); a `count` source matches a team member by its species or its base species, so the format relies on that preset for the exact formes. The preset is built from the transcribed tables in `src/lib/pkmn/preset-data/wichtelcup.ts` (names mapped to dex ids with `toID`; `WICHTELCUP_JUNK_ROLES` holds the reviewed primary role of each junk species), so the species are typed once. `wichtelcup-preset.server.test.ts` proves, with the real dex, that the document compiles with every entry a known species, that the four pools are disjoint and together equal the preset's allowlist, and that every listed species falls into exactly one pool by species or base species.

### Not yet covered

- The editor is form-based. There is no sentence or chip builder, no editing of threshold conditions (a condition is shown and can be removed), no flow canvas, no simulator and no AI drafting; views (combined standings) and legacy modules are preserved but not editable, and the base language and translation status of a text are not editable. There is no undo and redo, no version compare or restore, no "update available" prompt for leagues whose source format has a newer version, and saves are explicit (no autosave). Browser forward is not guarded while there are unsaved changes (back is). Exporting a format as a `.json` file and searching the list are not built.
- The shipped examples are code constants, not rows: they can be forked into a stored format, but there are no `kind = 'preset'` rows yet.
- No generated public rules page; public pages are unchanged. The descriptor does not check itself against live standings, and standalone tournaments have no descriptor (tournament-only admins see the examples only).
- Draws and forfeits are representable; forfeits are allowed by `CURRENT_ENV` (since `20261104090000`), draws stay off.
- `acquire.draft` is reserved. Inline rulesets (a stage names a ruleset by id or uses the season's) and ruleset lookups beyond an optional `env.rulesetIds`.
- A mock standings preview, the "try it" panel and machine translation of texts. The schedule preview estimates counts and weeks; it does not simulate a season.
- A bundle-size budget for the Studio client closure. Both languages of the kit catalogs ship on the admin routes that render the rules text; the routes are admin-only and route-split.
- Surfaces not built: an admin acting for a player (an `actor_id` is a 400), a first-class void of an accepted challenge (an admin removes the match with the match routes), notifications of any kind (the `notify` effect is planned but not delivered, see Events and effects; for a challenge expiry the defender learns of it by opening the play page), an admin UI for `rank`, `domain` and link-editing adjustments (API only), a holdings read for admins (a revoke lists the whole domain and the server refuses an impossible one; a refusal is neither stored nor audited, so a rostered admin who also plays can learn that a player does not hold an own-visibility item, an open decision), a `PlayerActionRule.review` queue (`review` is declared and read nowhere), substitution that migrates a replaced player's links, items and picks, a per-match attempt counter in the finalize heal (the heal handles 25 matches per run, oldest first), a snapshot of the registered team at replay submission (so a same-species edit of items, Tera or moves is only visible as evidence), and a compile warning for a `player.action` step that names an `admins` domain (a player can never pick from it; a submission against it answers `domain_locked`).
- German copy of the engine, player and admin surfaces is new and has had no native review.
