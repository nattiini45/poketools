# Match Module

## Overview
The Match module focuses on match/team stat aggregation helpers used by UI, reporting, and notification layers.

## File Structure
```
src/lib/match/
├── aggregation.ts  # Match/team aggregation helpers
├── aggregate-queue.ts  # Deferred aggregate processing
├── finalize.ts  # Shared completion side effects for manual/cron finalization
└── public-match.ts  # PublicMatch shape + allowlist mapper (client, cache and public-response boundary)
```

## Core Functions/Classes

### Team Aggregation
- **File**: `aggregation.ts`
- **Purpose**: Aggregate battle stats into display/report structures
- **Key Methods**: `aggregateTeamFromStats()`, `computePokemonScore()`, `computeQuickStats()`

### Match Children (reset)
- **File**: `match-children.ts` (`cleanMatchChildren`)
- **Team rows**: a match reset releases the match's team rows through `clearTeamsMatchPointer` (`src/lib/supabase/queries/teams.ts`), and `deleteMatchesByIds` does the same before a hard delete (`releaseTeamsFromMatches`). The pointer is cleared first (the completed-match lock lets a pointer-only change through), then a released match-prep row whose player already has a planned row (no `match_id`) in that tournament stops looking planned: it is moved to the player's personal teams (`tournament_id` NULL). It is never deleted: it is the player's roster (their teambuilder lists it, and the reset also deletes the match's `match_prep_teams`), and a library entry or share link on it keeps working. Without that, the player had two planned rows and `getPlayerTeamForTournament` / `getPlayerTeamForMatch` answered 500 (teambuilder, `POST /api/teams`, broadcast preview). A released row with no planned sibling becomes the planned row. The match reset runs the release inside the best-effort `cleanMatchChildren` (a failure is logged, the reset still succeeds); if the follow-up move fails after the pointer was cleared, the player is left with two planned rows and a retried reset cannot see them (no row is linked to the match any more). Repair by moving the newer row to the personal teams (`tournament_id` NULL). Proven on the local stack (rolled back): a direct delete of the linked row of a completed match is refused with `TEAM_MATCH_COMPLETED`, the release sequence goes through and leaves one planned row per player.

### Match Finalization
- **File**: `finalize.ts`
- **Purpose**: Centralizes completion side effects so manual confirmation and auto-confirm cron share the same behavior
- **Key Methods**: `finalizeMatchCompletion()`
- **EPB real kills wait for completion**: for an Evolution Point Buy season the step `epb_real_kills` credits the real kills of the match's games when the match reaches `completed` (opponent confirm, auto-confirm, admin dispute resolution), never at game submission, so a `pending_confirmation` or `disputed` result moves no tracker. Each game is credited once (`games.evolution_applied_at`, set by `epb_credit_game_kills` in the same transaction as the tracker increments; `supabase/migrations/20261020100200_games_evolution_credit.sql`), so a finalize re-run or the heal credits nothing twice. The matchday hooks (`epb_hooks`) run after it and are blocked when it fails. Aggregates are unchanged: every games / battle_stats write still enqueues its aggregate job at submission. Details, admin edit / delete / reset behaviour and the backfill of older games: [Evolution Point Buy](./evolution-point-buy.md#match-lifecycle-wiring).
- **Bracket propagation**: for single- and double-elimination tournaments it calls `propagateBracketOnMatchComplete()` synchronously (bracket integrity, not a background job). A propagation error does not undo the completed match: the result carries `propagation_failed: true`, an audit row `match.propagation_failed` is written, and an admin heals the bracket with repair-bracket. See [Tournament](./tournament.md) (Bracket Engine v2).

### Aggregate Queue
- **File**: `aggregate-queue.ts`
- **Purpose**: Processes deferred aggregate jobs and marks `games.aggregate_applied_at` after successful application
- **Atomic apply**: each job is applied by the `apply_aggregate_job` RPC (`supabase/migrations/20261018130100_aggregate_apply_atomic.sql`), which locks the job and the game, fences on the job status and the game marker, applies the aggregate and player deltas and sets `aggregate_applied_at` in one transaction. A job applied twice (a reclaimed job, a retry) counts once; a cancelled job applies nothing; bad deltas abort before any aggregate or marker changes.
- **Failures**: a job whose own processing fails goes back to `pending` (or ends `failed` once its attempts are exhausted) and is counted in `failed`; the run still succeeds. A failed claim throws `AggregateQueueClaimError`; a failed reclaim or queue write throws `AggregateQueueRunError` after the batch (fresh jobs are still applied first). The reclaim ends exhausted `processing` jobs as `failed` instead of returning them to `pending`.
- **Cron** (`/api/cron/process-aggregates`): answers 500 with a code per cause: `aggregate_claim_failed` (the claim RPC failed), `aggregate_queue_failed` (anything else in the run: the reclaim, a queue write, the revalidation after the batch), `aggregate_health_failed` (the health probe or the failed-job count errored), and `aggregate_jobs_stranded` when `aggregate_job_health()` reports pending rows that can no longer be claimed or rows stuck in `processing` for more than 15 minutes (three reclaim windows).
- **Jobs that ended `failed`** (attempts exhausted, or reclaimed with exhausted attempts) do not make the cron answer 500. The 200 body reports their total as `failedJobs` next to the run's `processed`, `failed` (this run, retried later) and `reclaimed`; a non-zero total is logged at error level on every run. Their games are not counted until an admin rebuilds the affected scopes; review them through the admin aggregate stats.
- **Scope rebuilds and the queue**: right after it clears the scope, `rebuildAggregatesForScope` reads the games that still have a live increment job (`pending` with attempts left, or `processing`; `listGameIdsWithLiveIncrementJobs`) and the newest game's `created_at`. It skips those games and lists only games created up to that moment: their own queue job counts them into the cleared scope, and the rebuild never sets `aggregate_applied_at`, so counting them too counted them twice once the job applied. A job that applies between the clear and that read (one round trip) is an overlap. Two more need a game recorded while the rebuild runs: `games.created_at` is the recording transaction's start time, so a recording that started before the fence read and committed after it passes the `createdUpTo` bound while its job applies after the clear; and `recordGameResult` writes the battle stats before it queues the job, so a rebuild page that reads the game in between counts it and the job counts it again. Each counts that game twice in the rebuilt scope; re-running the rebuild once the queue is idle repairs it, so do not rebuild while results are being recorded. (Skipping games with a NULL marker and no job would close both windows but would drop every game recorded before the queue existed, which has a NULL marker and no job.) Games whose job ended `failed` (or a pending row with exhausted attempts) are counted by the rebuild, as before, but keep `aggregate_applied_at` NULL: a later admin delete of such a game subtracts nothing (`not_counted`) and an edit re-applies its new stats on top of the rebuild's counts, so after deleting or editing such a game, rebuild its scopes again. A `processing` job on its last attempt counts as live, so the rebuild skips its game; if that attempt then fails, the job ends `failed` and the game is missing from the scope until the next rebuild (the cron reports it in `failedJobs`).
- **Scope rebuilds and game changes must not overlap**: `rebuildAggregatesForScope` (admin data tools, entity-delete rebuilds) clears a scope's rows and recounts its games in pages. A game edited or deleted while its scope is being rebuilt can be counted wrongly (its rollback or re-apply lands on rows the rebuild is clearing or has not reached yet); the rebuild sorts its writes, which prevents deadlocks, not this. Do not edit or delete games of a scope during its rebuild; if it happened, rebuild the scope again. The admin data tools say so next to the rebuild.
- **Admin game edit / delete**: `editGame` and `deleteGame` (and `resetMatch`, through the same helper) cancel the game's queued jobs FIRST and only then read `games.aggregate_applied_at` to decide the rollback (`readGameAfterJobCancel` in `src/lib/pkmn/game-pipeline.ts`). `apply_aggregate_job` holds the job row lock until it commits, so once the cancel has returned no queue job can apply that game any more; reading the marker before the cancel could miss a job that applied in between and count the game twice.
- **Atomic, fenced rollback** (`rollback_game_aggregates`, `supabase/migrations/20261018170000_aggregate_rollback_atomic.sql`): the rollback of one game decrements `aggregates` and `player_aggregates` AND clears `games.aggregate_applied_at` in ONE transaction, under the game row lock `apply_aggregate_job` takes too. It is fenced on the exact marker value the caller read together with the battle stats its deltas were built from (`buildGameAggregateDeltas`, the same builder the apply uses): every path that changes a game's stats clears the marker first and every apply sets a fresh `now()`, so a marker that still matches proves the deltas describe what was counted. Outcomes: `rolled_back`; `not_applied` (marker NULL); `marker_changed` (a concurrent edit re-applied the game); `game_missing`. The TS caller (`rollbackCountedGame` in `game-pipeline.ts`) only calls the RPC when the marker it read is set, so a sequential retry after a committed rollback reads NULL and never calls it; `not_applied` and `marker_changed` therefore both mean a concurrent edit or delete of the same game won the race, and the request stops with 409 `admin_game_changed_concurrently` before writing anything, so an edit never writes stats or an apply on top of the winner's. `game_missing`: a delete is done (the row is gone), an edit answers 404 `game_not_found`. Any error rolls back decrements and marker together. TS: `rollbackGameAggregates()` in `src/lib/supabase/queries/aggregates.ts`; the old three-request path (`rollbackAggregates` + marker clear) and the standalone marker writers are gone.
- **Race-free decrements**: `batch_decrement_aggregates` / `batch_decrement_player_aggregates` (same signatures, used only inside `rollback_game_aggregates`) now run one relative `UPDATE ... RETURNING` per delta under the row lock and delete a row only when the count it returned is 0 (re-checked in the DELETE). Before, they read the count without a lock and wrote the stale value back absolutely, so two decrements of one row (games of one match sharing a Pokemon, rolled back in parallel by `resetMatch`) lost one, and a decrement overlapping a queue apply could overwrite its increment. Applies and rollbacks take their row locks in the same sorted order (scope, scope id, Pokemon, player), so `resetMatch` keeps rolling a match's games back in parallel without deadlocks. `resetMatch` settles every game's rollback before it decides: when one loses a race (a concurrent edit or delete of that game) after siblings were already removed, it answers 409 `admin_match_reset_partial` (`MatchResetPartialError`, `count` = games already removed) and does not reset the match fields; the remaining games are still counted correctly and resetting again finishes the job (the admin UI offers a reload). When no game was removed, the game's own error (for example `admin_game_changed_concurrently`) is answered unchanged. The admin scope rebuild (`updateAggregatesForScope`, after `clearAggregatesForScope`) sends its `batch_upsert_*` deltas in the same order, so a rebuild overlapping a per-game apply or rollback cannot deadlock against it.
- **Edit re-apply is atomic**: `editGame` re-applies the new stats through `applyGameAggregatesNow` (`aggregate-queue.ts`): it inserts a job row already `processing` (the claim never picks it up) and calls `apply_aggregate_job`, so the increments, the marker and the job completion commit in one transaction. A lost response after the commit leaves the marker set, so a retried edit rolls that application back exactly once; an error inside the apply leaves neither increments nor marker. An outcome other than `applied` (a concurrent edit or delete won) throws `SyncAggregateApplyConflictError`.
- **Concurrency for edits: version claim plus edit lease**: the edit page and the inline editor on the match page pass the game's `updated_at` as they loaded it (`expected_updated_at` in `PATCH /api/admin/games/[id]`; without it the version the request read first). The match page reads the versions for editors only, BEFORE the match and its battle stats, so a change landing between those reads is caught too. Before anything else `editGame` claims the game's edit lease together with that version in ONE conditional UPDATE (`claimGameEditLease` → `claim_game_edit_lease`, `supabase/migrations/20261019100000_games_edit_lease.sql`): it succeeds only while `updated_at` still equals the editor's version AND no other edit holds an unexpired lease (`games.edit_lease_token`, `games.edit_lease_until`, database clock). Outcomes: two edits with the same version (a double submit, two admins on one game): exactly one claims it, the other answers 409; an editor reloaded while an edit runs holds the current version, so only the running edit's lease refuses it: 409 `admin_game_edit_in_progress` (`GameEditInProgressError`); an editor opened before the last change: 409 `admin_game_edit_stale` (`GameEditStaleError`). A refused edit writes nothing, for a game whose marker is NULL too, where no rollback fence exists. The lease is released when the edit ends, success or failure (`releaseGameEditLease`, fenced on the token; the release moves the version on, so an editor opened during the edit is stale afterwards), and expires after `GAME_EDIT_LEASE_TTL_SECONDS` (120 s) when the process died or the release failed. A failed or lost release is logged and does not fail a saved edit; its only effect is that further edits answer 409 `admin_game_edit_in_progress` until the lease expires. A save claims the version first, so a failed save moves it on as well: retrying from the same editor answers `admin_game_edit_stale`, whose text says the change may be the admin's own earlier attempt. Deletes and match resets take no lease; they meet a running edit at the rollback fence and the fenced delete (409 `admin_game_changed_concurrently` / `admin_game_delete_recounted`). The admin UI offers a page reload for every one of these 409s (`GameChangeAlerts`). Local proof (local stack, `src/lib/pkmn/__tests__/game-edit-concurrency.local.test.ts`): two concurrent saves with the same version of a counted game and of an uncounted game without stats each left exactly the winner's stats, counted exactly once, with the loser refused; an editor reloaded while an edit was held right after its claim was refused with `admin_game_edit_in_progress`, wrote nothing, and the running edit's stats were counted once; an expired lease left behind was claimed by the next edit.
- **Change failure heals itself**: from the job cancel on, the game may be uncounted (rolled back, or its pending job cancelled). When any step up to the re-apply fails (the rollback, the winner or stats write, the apply), `editGame` queues a fresh pending job for the game (`enqueueAggregateJob`) and rethrows the original error; the queue then counts the game's stats as they are in the database, and `apply_aggregate_job` fences on the marker, so the job is a no-op when the game is still or again counted. The delete path (`deleteGame` and `resetMatch`, through `rollbackAndDeleteGame`) does the same when its stats read, rollback or fenced delete fails. Not re-queued: a lost race (`admin_game_changed_concurrently`, the winner owns the count) and a game that is gone. If the re-queue itself fails, the request re-reads the game: when it is gone (deleted concurrently, so nothing is left to count) the original error is rethrown; otherwise it answers 500 `admin_game_left_uncounted` (`GameLeftUncountedError`, carrying both errors, logged by the route), so the admin is told the game may be missing from the statistics and that a scope rebuild of its tournament and season (admin data tools, linked from the error) is the recovery.
- **Fenced delete (closes the edit-vs-delete race)**: the delete removes the game row in ONE statement fenced on the marker being NULL (`deleteUncountedGameRow` in `src/lib/supabase/queries/games.ts`; `battle_stats`, `aggregate_jobs` and `broadcast_moments` go with it by `ON DELETE CASCADE`). A concurrent edit's re-apply sets the marker under the game row lock, and a DELETE that waited on that lock re-checks its WHERE against the committed row, so a re-apply that committed first leaves the game in place and the delete answers 409 `admin_game_delete_recounted` (`GameRecountedConcurrentlyError`: the game still exists and its counts match it as it now stands; this request's rollback, if any, was followed by the edit's re-apply); a delete that committed first makes the apply answer `game_missing` and count nothing. Before, two admins editing and deleting one uncounted game at the same moment could leave the edit's counts behind for a deleted game. Local proof (local stack): both orders in two sessions.
- **EPB recheck after an admin change**: the edit (and the legacy delete/reset path) re-checks evolution progress after the game change committed. For an EPB season the edit debits a credited game's real kills by its old stats (`epb_uncredit_game_kills`, fenced on the `games.evolution_applied_at` value read before the edit's writes) because the edit moves the match out of `completed`; the edited stats are credited at the next completion. After the debit the edit re-reads the match and credits the edited stats at once when a concurrent confirm completed it during the edit, also when that confirm landed between the status change and the debit (its finalize still saw the old marker and credited nothing, so without the re-read the completed match would lose the game's kills); a confirm after the re-read finds the marker cleared and its finalize credits the edited stats. EPB delete and reset rebuild the season, which re-syncs the markers (see [Evolution Point Buy](./evolution-point-buy.md#match-lifecycle-wiring)). A failure there is logged with its cause and reported in the result as `evolution_recheck_failed: true` (catalogue warning `admin_game_evolution_recheck_failed`); it is never an empty success. The admin game UI (edit form, per-game delete and match reset in `AdminMatchActions`) shows it as a warning with a link to the admin data tools, and shows `admin_game_match_status_conflict` (saved, status not re-evaluated) and the 409 refusals above with a reload action (`src/lib/match/game-change-outcome.ts`, rendered by `src/components/match/GameChangeAlerts.tsx`; the edit page, the inline editor `GameDetailEditForm` and `AdminMatchActions` send their requests through its `gameEditRequest` / `sendGameChange`). The inline editor keeps itself open after a save that carries a warning, with Save disabled and a Close button. Record Reconciliation repairs the evolution state. `resetMatch` on a match that is already scheduled throws `MatchAlreadyScheduledError` (409 `match_already_scheduled`); the cascade skips such a child by that type, not by message.
- **Deploy order**: apply the migrations before the code, which calls `apply_aggregate_job`, `aggregate_job_health` and `rollback_game_aggregates`. Pending rows left with exhausted attempts by the old reclaim keep the cron at `aggregate_jobs_stranded` until the repair in the migration header runs.
- **Local proof** (2026-10-18, local stack): success, apply-twice-counts-once, duplicate job (`already_applied`), cancelled job, job/game mismatch, bad deltas rolled back after the first upsert ran, reclaim (exhausted ends `failed`, others back to `pending`), health counts, and EXECUTE for `service_role` only; the edit re-apply sequence through a `processing` job (applied once, a retry after a committed apply counts once, a failed apply leaves no increments and no marker, an abandoned edit job is reclaimed to `pending` or cancelled by a retried edit); plus two concurrent applies of one game (one `applied`, the other waits on the game row lock and answers `already_applied`) and a cancel during an open apply (waits, cancels nothing, the marker read after it is set). `game_missing` cannot happen while `aggregate_jobs.game_id` cascades on delete: the job disappears with the game and the fence answers `job_not_processing`. Rollback (local stack): `rollback_game_aggregates` in BEGIN ... ROLLBACK (wrong marker → `marker_changed` and nothing changed; matching marker → decrements, a row reaching 0 deleted, marker cleared; retry → `not_applied`; unknown game → `game_missing`; non-array deltas → 22023; EXECUTE for `service_role` only), then two sessions on committed rows: a second rollback of the same game started while the first held its transaction waited and answered `not_applied` (decremented once), a rollback of another game sharing the Pokemon rows waited and decremented on top (3 → 1, no lost update), and a call that failed in its player deltas left the aggregate decrement and the marker unchanged.

### Public Match Shape
- **File**: `public-match.ts` (pure, type-only imports: safe in server and client modules)
- **Purpose**: The only match fields that may reach a `'use client'` component, a public read-cache entry or a public API response.
- **Shape**: `PublicMatch` is `MatchWithPlayers` without the admin-only columns `notes` (admin notes / dispute log), `submitter_id`, `auto_confirm_at` and `confirmed_at` (`PRIVATE_MATCH_FIELDS`). Everything else stays, `social_image_url` (the public social card) and every `GameSummary` field included (`PUBLIC_MATCH_FIELDS`, `PUBLIC_GAME_FIELDS`).
- **Key Methods**: `toPublicMatch()`, `toPublicMatches()`. They copy each field by name (never a spread) and pass values through unchanged; a compile-time check fails the build when a `MatchWithPlayers` key is neither public nor private, so a new `matches` column must be classified.
- **Who gets full rows**: admins, resource admins of the match's tournament or league, and the match's own participants. Everyone else gets `PublicMatch`.
- **Database boundary**: the same four columns are closed at the database for direct REST and GraphQL callers. `anon` and `authenticated` hold no privilege on `public.matches` (`supabase/migrations/20261008081402_revoke_anon_private_match_columns.sql`), nor on anything else in `public` (`20261008081443_close_public_api_roles.sql`), so the browser anon key reads no match column at all. With both applied, an anon `GET /rest/v1/matches` answers 401 with code 42501. Objects created later from the dashboard as `supabase_admin` are not covered, because its default privileges still grant the API roles; check them with V7 and V10 (`docs/security/anon-match-columns.md`). The opt-in LIVE-LOCAL test `src/lib/supabase/__tests__/api-role-grants.local.test.ts` proves it on a local stack; `src/lib/supabase/__tests__/migration-api-grants.test.ts` fails if a migration reopens the table (a grant, a default privilege, role membership, or a recreated table without the close-out). A restored dump does not carry the revokes, so every restore re-runs both migration files above.
- **Where it is applied**: `assembleLeagueSchedule` (`LeagueFixture.match` is `PublicMatch`, so the league schedule and the world payload hold no private columns) and again in `assembleWorldRouteData`; `publicReads.tournamentMatches` (inside the cache callback); the creator `/content` page; `GET /api/matches/[id]`; `GET /api/matches/head-to-head` (served from `publicReads.tournamentHeadToHead`, which maps inside its cache callback); `GET /api/tournaments/[id]/rounds/[rid]` (`RoundWithMatches.matches` is `PublicMatch[]`). The public read-cache entries that hold matches are named `tournament-matches-public`, `tournament-h2h-public`, `world-route-data-public` and `league-schedule-public`, so entries cached before the narrowing (which held the notes) are never served.
- **Notes on the match detail page**: `/tournaments/[id]/matches/[mid]` renders the notes only for a site admin confirmed by the live `getLiveAccess()` read, never by the session copy. The page returns 404 for a malformed (non-UUID) tournament or match id, before any query, and for a match whose `tournament_id` is not the URL's tournament.
- **Admin match pages**: `/admin/matches/[id]`, `/admin/matches/[id]/import-replay` and `/admin/matches/[id]/games/[gid]/edit` need more than `AdminGuard`'s any-admin check. The viewer must be a site admin or a resource admin of that match's tournament or its league: `canAdministerMatch(match.tournament_id)` in `src/app/admin/matches/[id]/match-access.tsx`, decided from the live `getLiveAccess()` read. Any other admin gets `MatchAccessDenied`, so the notes and override controls never render for an admin of an unrelated tournament or league. This is the same rule as `POST /api/admin/matches/[id]/reset` and `/api/admin/games/[id]`. The match page's back link restores the Matches list with its filters: the list links to it with `?back=<list query>`, and `parseMatchListBack` (`src/lib/admin/match-list.ts`) re-validates that value, so only known keys survive and the href is always a same-origin `/admin/matches` path. The replay import and the game edit pages carry the same `?back=` and return to the match page with it (`matchPageBackSuffix`).

## Social Images
- **Route**: `POST` and `DELETE /api/matches/[id]/social-image`, site admins only (`requireAdmin()`). The match page's `CreateSocialImageButton` captures the match card, POSTs it, and calls `router.refresh()` after the 201 so the page shows the new URL.
- **Naming**: each upload is a NEW object in the `social-images` bucket at `matches/<matchId>/<uuid>.png`, written with `cacheControl: '31536000'` (one year) and `upsert: false`. An object is never overwritten; `matches.social_image_url` is updated to the new URL.
- **Re-upload keeps the old object** on purpose: a Discord or social post made with the old URL keeps its image.
- **DELETE** removes only the object the stored URL names, and only when `socialImagePathFromUrl` (`src/app/api/matches/[id]/social-image/storage-path.ts`) accepts it: the project's own origin, the `social-images` bucket, and a path of THIS match (the legacy `matches/<id>.png` or `matches/<id>/<uuid>.png`). A foreign, other-match or path-escape URL clears the column without touching Storage. A failed removal returns 500 `STORAGE_REMOVE_FAILED` and keeps the URL.

## Data Flows
- **Input**: Battle stats grouped by game + player IDs
- **Processing**:
  1. Fold per-game stats into per-Pokémon totals
  2. Compute survivor-based Pokémon score
  3. Compute quick KO summaries
- **Output**: Aggregated team and scoreboard structures

## Confirm and dispute (`/api/confirm-match/[mid]`)
- **Guarded update.** The status change is a compare-and-set on the status the route read. When it misses, the route re-reads the match: a missing match answers 404 `match_not_found`; a match that is already in the requested state (same status and, for a completion, the same winner, with no admin notes that would be discarded) answers 200 with the current match, as a repeated click should; any other state answers `409 match_state_changed` with `params.status` (the current status) and writes nothing: no revalidation, no finalize, no Discord event. Before, a lost race (for example a dispute landing between a Complete click and the request) answered success.
- **Submitter is kept.** `matches.submitter_id` is set only when it is empty, for admin and participant confirms and disputes alike, so a confirmation or an admin override no longer overwrites the player who reported the result. A dispute therefore does not record the disputer in that column: the disputer is the actor of the `match.dispute` audit event and is named in the Discord event. Participants cannot send notes (only admins write `notes`).
- **Audit.** Every dispute, by a player or an admin, writes one `match.dispute` audit event (status change, `metadata.reason`, `metadata.by_admin`; see "Dispute details"). An admin confirm writes `match.override` when it sets a winner or notes or resolves a disputed match. A participant's own confirm writes no audit event.
- **`date_played`** stays the completion stamp: it is only ever set when a match completes, so there is no earlier play date to overwrite.
- The admin match page asks for confirmation before Complete and Dispute and shows the recorded series tally with warnings; see [Admin](./admin.md).

## Scheduling and Auto-Confirm
- Match scheduling uses `rounds.deadline`, `matches.scheduled_at`, and `match_proposals`.
- Proposal routes are participant-only and keep writes API-owned.
- Auto-confirm uses `matches.auto_confirm_at`: replay results use a 24h window, manual results with screenshots use 48h, and manual results without screenshots stay in admin review.
- Completion side effects must go through `finalizeMatchCompletion()` to avoid divergence between manual confirmation and cron completion.

## Admin Match Page Verbs

`/admin/matches/[id]` (module doc [Admin](./admin.md)) offers the verbs below. Every route behind them uses `authorizeMatchAdmin` (`src/lib/auth/match-admin.ts`): a signed-in site admin, or a resource admin of the match's tournament or its league (the rule of the reset route and of `canAdministerMatch`). Anyone else gets 403 `forbidden`; an unknown match is 404 `match_not_found`; a bad body or query is 400 `validation_failed`. The shared types and limits (reason length 500, history page size) live in the client-safe `src/lib/admin/match-detail.ts`.

### Schedule

- `PATCH /api/admin/matches/[id]/schedule` with `{ scheduled_at }`: an ISO instant with an offset (between the years 2000 and 2100), or `null` to clear the time. The answer is `{ scheduled_at, previous_scheduled_at, proposals_cancelled, proposals_cancel_failed, unchanged }`.
- A **completed** match cannot be rescheduled: 409 `match_schedule_completed` (also when the match completes between the read and the write). Reopen it first.
- The same instant as the stored one is a no-op (`unchanged: true`): no write, no audit event, no proposal change.
- A change (set, move or clear) cancels every pending time proposal of the match (`cancelPendingMatchProposalsForMatch`, status `cancelled`), so a stale proposal cannot reschedule the match later. The page warns before saving when open proposals exist. The cancel runs after the time is committed: if it fails, the time stays saved, the audit event and the revalidation still run, the answer carries `proposals_cancel_failed: true` and the page shows a warning.
- Audited as `match.schedule` (see [Audit](./audit.md)). Unlike the proposal accept route, this write needs no participant: it is the organizer's override.

### Reopen (without a reset)

`POST /api/admin/matches/[id]/reopen` with `{ reason }` (required, 1 to 500 characters after trimming; rate limit 20 per hour and admin) moves a `completed`, `pending_confirmation` or `disputed` match back to `in_progress` (`reopenMatch`, `src/lib/match/reopen.ts`). The games are kept; the result is withdrawn.

- **Transitions**: `ADMIN_TRANSITIONS` in `src/lib/tournament/match-state.ts` gained `completed -> in_progress` and `disputed -> in_progress` (`pending_confirmation -> in_progress` existed). `canReopenMatch(status)` is the pure check. This is safe because the table is admin-only (`validateTransition` still refuses a non-admin with `match_reset_admin_only`) and no code path outside the confirm-match route and the game pipeline reads it. A `scheduled` or `in_progress` match answers 400 `match_transition_invalid`. The `disputed` entry is a deliberate small extension: a disputed match never finalized, so there is nothing to reverse.
- **Always reversed** (one compare-and-set write on the status the reopen read): status `in_progress`; `winner_id`, `auto_confirm_at`, `confirmed_at`, `date_played` and the finalize marker are cleared. `submitter_id` and the games stay. A lost compare-and-set answers 409 `match_state_changed` with nothing changed (with `params.status`, the status the match has now, when the re-read succeeds).
- **Also reversed for a completed match** (isolated post-commit steps, each logged on failure): the round status when the round had completed (`revertRoundIfCompleted`); later empty bracket slots the winner had filled (`unpropagateBracketOnMatchReset`, deletes only empty scheduled matches); the match analysis, prep analyses, snapshots and social image; both players' ratings and rating history, streaks and signatures (`rebuildGamificationAfterUncomplete`); and the evolution progress (`repairSeasonEvolution` for an Evolution Point Buy season, a recheck otherwise). A `pending_confirmation` or `disputed` match needs only the status write.
- **Not reversed**: achievements already granted (permanent, as for reset and game delete) and a Discord or social announcement already sent. The dialog says so.
- **Refusals before any write** (completed match only): a later bracket match the winner advanced into that has results or is in progress answers 409 `match_reopen_downstream_played` (`{count}`): reset those later matches first. A rating history that cannot be rebuilt (`planRatingRebuild` refuses) answers 409 `rating_history_incomplete`.
- **Incomplete reopen**: the status change is committed before the follow-up steps. When a step fails the route still writes the audit event (`incomplete: true`, `failed_steps`) and answers 500 `match_reopen_incomplete` (`{count}` failed steps). Run the season reconcile for the match's season ([Reconcile](./reconcile.md)) to repair ratings, streaks and evolution progress. The page closes the dialog, reloads, and shows the message as a warning in the reopen section.
- **Finishing again**: nothing moves the match to `pending_confirmation` by itself. Finish it with the Admin Override form or a game edit. A reopen that races a finalize still in flight can leave ratings applied after the rebuild; the season reconcile repairs it.
- Audited as `match.reopen`.

### Dispute details

- `POST /api/confirm-match/[mid]` accepts an optional `reason` (1 to 500 characters) with `action: 'dispute'`; with `confirm` it is a 400. The player form (`ConfirmMatchClient`) shows an optional textarea with a counter. An admin who disputes through the Admin Override form gives the notes text as the reason. The reason is never stored in `matches.notes` (that stays admin-only).
- Every successful dispute, by a player or an admin, writes one `match.dispute` audit event (`changes.status`, `metadata.reason`, `metadata.by_admin`). Player disputes were not audited before. A dispute keeps the original reporter in `matches.submitter_id` (see "Submitter is kept" above) and the disputer is the actor of the audit event. The `match.override` event covers only the move to `completed`, so an admin dispute produces exactly one event.
- The admin match page shows a dispute panel for a disputed match: who disputed (with an admin marker), when, the reason, and the reported winner and reporter. It reads the newest `match.dispute` event (`getLatestMatchDispute`). A match disputed before this change has no event: the panel says the details were not recorded. The audit write is fire-and-forget, so a lost write shows the same state.

### Reset and delete-game reasons

- `POST /api/admin/matches/[id]/reset` accepts `{ cascade?, reason? }` and `DELETE /api/admin/games/[id]` an optional JSON body `{ reason? }` (an empty body still works). A reason lands in the audit metadata (`match.reset`, `game.delete`) as `metadata.reason`. It is optional on the API so existing callers keep working; the admin page makes it required.
- `GET /api/admin/matches/[id]/reset-preview` is read-only and returns `{ games_to_delete, was_completed, downstream }`, where `downstream` lists the played later bracket matches a cascading reset would also reset (deepest first, with player names, status and round name). A scheduled match answers zeros. The reset dialog shows it, so the admin sees the impact before confirming; if the preview fails the dialog keeps the old flow (post without cascade; the 409 `DOWNSTREAM_PLAYED` answer, with its `{count}`, opens the cascade dialog). The preview reads every match of the tournament, so it is for the dialog only, not for list pages.

### History

- `GET /api/admin/matches/[id]/history?offset=0&limit=20` returns `{ entries, total, offset, limit }`, newest first (`listMatchAuditEvents`, `src/lib/audit/queries.ts`). `limit` is 1 to 50 (default 20), `offset` 0 to 1000 (default 0); anything else is 400. Same access rule as the other verbs, so a resource admin reads the history of their own matches only.
- **Included**: audit events with `resource_type` `match` and this id, plus events with `resource_type` `game` whose `metadata.match_id` is this id (`game.edit`, `game.delete`). Each entry has the action, the actor name, the time, the reason (`metadata.reason`) and the before/after `changes`. The client IP is never returned.
- The page renders the first page on the server and loads more on demand; the panel remounts when a refresh brings a new first page, so an action's own event shows at once. The History, dispute-details and time-proposal reads are optional: if one fails the page logs it and still renders its controls (History shows its Retry notice). The `metadata->>match_id` filter has no index; the paging bounds keep it cheap, and an expression index on the audit table is a follow-up.

### Admin override and a changed match

The Admin Override form in `POST /api/confirm-match/[mid]` is a compare-and-set on the status the admin saw (see "Guarded update" above). When the match changed in between (`updateMatchStatus` finds no row to update) and is not already what the admin asked for, the admin gets 409 `match_state_changed` instead of a success, and the page reloads. A repeated click on a request the match already satisfies (a double click on Confirm with the same winner and no admin note) keeps the idempotent success answer, for a participant and for an admin alike.

## Replay Binding

Since 0.2.3; migration `supabase/migrations/20261020100000_games_replay_hash.sql`; module doc [PKMN](./pkmn.md) ("Replay binding").

- **One battle, one game.** A game recorded from a Showdown replay stores the replay's hash (`games.replay_hash`, SHA-256 of the canonical battle log, `src/lib/pkmn/replay-identity.ts`) in the insert that records the result. The hash is unique wherever it is set, across all matches and tournaments. A battle already bound to a game is refused with 409 `replay_already_recorded` before anything is written: the pipeline reads first, and `createGame` maps a violation of the unique index `games_replay_hash_key` to the same error, so two concurrent submissions of one battle cannot both land. The per-match URL check (409 `duplicate_replay`) still runs first.
- **The result comes from the hashed replay.** `recordGameResult` takes a replay result as `{ source: 'ps_replay', replay: BoundReplay, side_player_ids }`. The winner is the player of the side the log's `|win|` line names; the battle stats are the parsed rows of each side. No client-supplied winner or stats reach a replay game. A log that names no winner is 400 `replay_winner_unknown`; a side outside the match is 400 `match_player_not_participant`; both sides on one player is 400 `replay_sides_not_distinct`.
- **`POST /api/parse-replay`**: the sides come from the PS usernames (the legibility gate: `name_mismatch`, `replay_player_not_in_match`).
- **`POST /api/admin/matches/[id]/replay-preview`**: parses without the gate and returns the stats, side suggestions and `replay_hash`; a battle already recorded is 409 `replay_already_recorded` here already.
- **`POST /api/admin/matches/[id]/replay-import`**: the body is `{ replay_url, replay_hash, side_player_ids: [p1Player, p2Player] }`. The organizer only assigns the sides (the form shows the replay's winner and stats read-only); the route fetches the replay again and refuses it with 409 `replay_changed_since_preview` when it no longer hashes like the preview. Corrections after the import go through the admin game editor (`/admin/matches/[id]/games/[gid]/edit`), which marks the game `stats_locked`. The audit event `game.import_replay` records the hash, the winner and each side's PS name and player.
- **Manual results** (`POST /api/manual-result`) carry no replay and no hash.
- **Older games**: replay games recorded before 2026-10-20 keep `replay_hash` NULL until a maintainer runs `scripts/backfill-replay-hashes.ts` (dry run unless `--write`; it writes nothing when any two games would share a hash and lists them; one request per second to replay.pokemonshowdown.com; `npx tsx --env-file=.env.local scripts/backfill-replay-hashes.ts`). Until then a NULL row does not block a new submission of its battle in another match.
- **Deploy order for `20261020100000`**: the new code writes `replay_hash` on every game insert, so it must not be deployed before the migration (unknown column). Apply the migration, then deploy, then run the backfill dry run.
- **Residual gaps (known, open)**:
  - The game row (with its hash), its `battle_stats` rows and its aggregate job are separate inserts, not one transaction. When the stats insert or the job enqueue fails after the game row is written, `recordGameResult` deletes that game again before the error reaches the caller (`deleteUncountedGameRow`, fenced on `aggregate_applied_at`, stats and jobs cascade), so the battle can be submitted again; the hash stays bound until that delete, so the unique index still refuses a concurrent submission of the same battle meanwhile. Only when that delete fails too (logged with the game id) does the game remain without stats or without a job, keeping the hash: every new submission of that battle answers 409 `replay_already_recorded` until an admin deletes that game (admin game delete; the match page lists it without stats). A concurrent submission to the same match can briefly see the doomed game (its game number is skipped; its win can count toward a Bo threshold read in that window). An atomic `record_game_result` RPC (see "Concurrent submissions" below) would close both.
  - Replay games the backfill cannot fetch (the replay was deleted on Showdown, made private, or the request fails) keep `replay_hash` NULL. They are only covered by the per-match URL check, not by the cross-match battle check: the same battle can still be recorded once more in another match.

## Battle Stats: one row per Pokémon

Since 0.2.3; migrations `supabase/migrations/20261020100100_battle_stats_unique_pokemon.sql` and `supabase/migrations/20261021100200_battle_stats_pokemon_key_js_trim.sql`.

- A game holds at most one `battle_stats` row per player per Pokémon, compared case- and padding-insensitively: unique index `battle_stats_game_player_pokemon_key` on `(game_id, player_id, lower(regexp_replace(pokemon_name, '^[set]+|[set]+$', '', 'g')))`, where `[set]` is exactly JavaScript's trim set (WhiteSpace + LineTerminator), so the index compares the key `battleStatPokemonKey` (`name.trim().toLowerCase()`) the schemas use. `20261021100200` rebuilt the index under the same name; `20261020100100` had keyed it on `lower(btrim(pokemon_name))`, which strips only spaces. The request schemas refuse a repeat first with 400 `validation_failed` (manual result and the admin game edit, `src/lib/validation/schemas.ts`); the index is the backstop for any other writer, and `createBattleStats` maps its violation to 409 `battle_stats_duplicate_pokemon` (the insert writes no row). The same Pokémon on both sides (a mirror) is fine.
- **Deploy order for `20261020100100` and `20261021100200`**: each migration's DO block fails loudly and deletes nothing when a game already holds such a repeat under its key (for `20261021100200`: names that differ only in leading or trailing non-space whitespace); fix that game in the admin game editor and apply again. `20261021100200` drops and recreates the index in one transaction (ACCESS EXCLUSIVE lock on `battle_stats` while it rebuilds; check the live row count first).

## Finalize Integrity and Heal (runbook)
Migration `supabase/migrations/20261018130000_match_finalize_integrity.sql`.

- **Marker**: the status flip to `completed` commits before finalize runs. Finalize runs each side effect as a guarded step (`FINALIZE_STEPS` in `src/lib/match/finalize.ts`), logs each failure with its error, and stamps `matches.finalized_at` only when every step succeeded. Every status write clears the marker, so a completed match with `finalized_at IS NULL` is one whose finalize did not finish. A failed run writes the audit event `match.finalize_failed` with `failed_steps`, `healed_automatically` and `needs_admin`.
- **Audit event**: `match.finalize_failed` sorts the failed steps by what the heal does with them: `healed_automatically` (re-run), `verified_by_heal` (ratings: never re-applied, only checked; the heal finishes the match by itself when both `rating_history` rows exist, otherwise the cron lists it under `needsAdmin`), and `needs_admin` (achievements, announcements: never re-run).
- **What the caller sees**: `POST /api/confirm-match/[mid]` answers 500 `match_finalize_incomplete` (`{count}` failed steps) when a step failed; the completion stays. The auto-confirm cron answers 500 `auto_confirm_partial_failure` (`{count}` failed matches, match ids and step names in `details`) when a confirm, a finalize step or a heal failed.
- **Needs-admin rows**: a completed, unfinalized match whose `rating_history` rows are missing (`ratings_missing`) or whose winner is not one of its players (`winner_not_participant`) can only be finished by an admin. The cron reports these as `needsAdmin: [matchIds]` in its JSON body (details with the reason under `heal.needs_admin`), logs them in ONE error line per run, and answers 200 when they are the only problem. They get no schema of their own: they stay on the worklist until an admin repairs them (runbooks below).
- **Heal**: each auto-confirm cron run walks the completed, unfinalized matches older than 10 minutes, oldest first (`updated_at`, then `id`), in keyset pages of 100 (`listMatchesNeedingFinalize` with a cursor). One batched `rating_history` read per page classifies the needs-admin rows (`findMatchesNeedingAdmin`), which are reported without a heal call; the scan pages past them, so they can never starve healable rows behind them. It attempts at most 25 heals and reads at most 10 pages per run; a run that stops at the page cap with rows left sets `heal.scan_truncated` and logs it (more than 1000 needs-admin rows waiting). The heal re-runs only the replay-safe steps (`FINALIZE_HEAL_POLICY`: revalidate, streaks via `recomputeStreaks`, signatures, EPB real kills (every heal: a game already credited answers `already_applied` and writes nothing), EPB hooks while the match has no snapshots, bracket propagation), verifies ratings, and never re-runs achievements or announcements. A success writes `match.finalize_healed`. A match reset meanwhile is skipped and logged, is not a failure, and does not use the attempt budget.
- **A confirm write that throws**: the cron re-reads the match and logs whether the completion committed anyway (a lost response or the 10 s request timeout after the UPDATE committed) or never landed. It never finalizes in that case (a concurrent confirm may be finalizing the same match); a committed completion is picked up by the heal after the grace period and, because finalize never ran, is listed under `needsAdmin` (`ratings_missing`) until an admin rebuilds ratings.
- **Runbook: `needsAdmin` lists a match with `ratings_missing`.** The heal never re-applies ratings. `updateRatings` writes both `player_ratings` rows and both `rating_history` rows in one transaction (`rating_apply_match_result`), but rows left by the earlier two-statement path (ratings written, history missing) cannot be told apart from a run that never happened, so the heal still only verifies. Fix: run the season reconcile for the match's season (rating rebuild, see [Reconcile](./reconcile.md)); once both `rating_history` rows exist, the next cron run heals the rest and stamps the marker. Find the match id in the cron's `needsAdmin` or in the `match.finalize_failed` audit event.
- **Runbook: the audit event's `needs_admin` lists `achievements` or `announcements`.** These are never re-run (repeatable achievements would count twice; posts go out at most once). Backfill achievements by hand if needed; a lost Discord or social post is not re-sent.
- **Runbook: `needsAdmin` lists a match with `winner_not_participant`.** A completed match whose winner is not one of its players is a data error the heal cannot repair. Fix the match through the admin match page (reset or confirm with a participant winner).
- **Concurrent submissions**: `UNIQUE (match_id, game_number)` turns a lost game-number race into 409 `match_result_conflict` before anything is written, and match status writes in the game pipeline are compare-and-set; a lost compare-and-set on the Bo threshold is logged with the match, game and both statuses. Residual (open, Phase B): the non-completed check is a read and the game insert carries no status condition, so a submission that read the match before a concurrent decision can still commit its game, its stats and its aggregate job. Only its status write is refused. Two submissions of the same replay can no longer both insert: the unique `games.replay_hash` index refuses the second with 409 `replay_already_recorded` (see Replay Binding); two identical manual entries still can. An atomic `record_game_result` RPC (status check and insert under one lock) would close this.
- **Admin game edit or delete during a concurrent status change**: the game change is saved and audited, the concurrent writer's status is kept, and the route answers 409 `admin_game_match_status_conflict`. Reload the match and check its status. An admin edit or delete of a COMPLETED match moves it to `pending_confirmation` (or `in_progress` / `scheduled`) without `validateTransition`; `match-state.ts` lists `completed -> scheduled` and `completed -> in_progress` for admins (the reset and the reopen, see "Admin Match Page Verbs") but not `completed -> pending_confirmation`, so adding the validation needs that table changed first (open follow-up). Ratings, rating history, streaks and signatures do follow the match: `deleteGame` and `editGame` plan the rating rebuild before any write (a history-gap cycle answers 409 with nothing changed, as in `resetMatch`) and, once the match has left `completed`, rebuild both players' ratings and recompute their streaks and signatures (`deleteGame` lists them in `recalculation.ratingsRebuilt`, `editGame` in `ratings_rebuilt`). Achievements are permanent and not revoked. The rebuild runs after the game change is committed: if it throws, the route answers 500 with the game already deleted or edited (a retried delete answers 404), and when the status write lost a race (`admin_game_match_status_conflict`) the rebuild is skipped. In both cases run the season reconcile for the match's season (see [Reconcile](./reconcile.md)) to rebuild the two players' ratings and streaks.
- **Deploy order for `20261018130000`**: every match status write now sends `finalized_at`, so code deployed before the migration fails every status write (unknown column). On production, first run the duplicate pre-check (`SELECT match_id, game_number, count(*) FROM games GROUP BY 1, 2 HAVING count(*) > 1;`, must be empty) and look at the `games` row count (the UNIQUE constraint takes an ACCESS EXCLUSIVE lock while it builds), then apply the migration, then deploy the code. Say so in the PR description.
- **Local proof**: `src/lib/supabase/queries/__tests__/match-finalize-integrity.local.test.ts` (LIVE-LOCAL, opt-in with `LOCAL_SUPABASE_FINALIZE=1` plus the local URL and keys on the command line) exercises the unique constraint (including two racing inserts), the marker (including `updateMatchPlayers`), the worklist keyset cursor through real PostgREST, the rating replay cursor past 1000 rows and the live rating writers against a local stack. The SQL-level proofs (index, backfill statement, grants: `anon` and `authenticated` hold nothing on `matches.finalized_at` or `games`) were run on the local stack on 2026-10-18.
