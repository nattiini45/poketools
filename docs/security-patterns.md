# Security Patterns (OWASP)

> Full OWASP-mapped security rules, the mandatory error-handling pattern, and the input-validation pattern for this repository.

The always-needed subset (auth guards, `safeErrorResponse()`, error transparency, ownership checks) lives in [`AGENTS.md`](../AGENTS.md#security-requirements); this doc holds the complete patterns an agent needs when writing or reviewing API routes, auth, or validation code. Load it when a task touches `src/app/api/**`, auth helpers, or request-body handling.

## OWASP Top 10 (2021) Mapping

Every agent writing code in this repo must follow these patterns. They map to the [OWASP Top 10 (2021)](https://owasp.org/Top10/) categories.

### A01 — Broken Access Control

- Every protected API route MUST call `requireAuth()`, `requireAdmin()`, `requireCreator()`, or `requireResourceAdmin()` from `src/lib/auth/helpers.ts` as its first operation.
- Resource ownership checks (e.g., `team.player_id !== player.playerId`) must happen in the API route, never in client components.
- Auth helper hierarchy: `requireAuth()` → `requirePlayer()` → `requireAdmin()` / `requireCreator()` / `requireResourceAdmin(type, id)` / `requireDraftAdmin(poolId)`. Player routes of a running league format use `requireSeasonMember(rawId)` (`src/lib/auth/season-member.ts`: a live `requirePlayer()` plus league participation, no site-admin bypass; the actor is always the session player and a body that names one is a 400) and `assertSeasonOpenForPlay` before a write; a hidden relation side, a pick or a team-audit subject is never serialised to a player (`docs/format-kit.md`, Live format routes).
- Public routes (dex search, calc, usage stats, broadcast overlays, wiki pages) are intentionally unguarded — document with a comment: `// Public: no auth required`.
- `requireSuperadmin()` is for the few actions a site admin must not take (restoring a league from the trash, the pending-rebuild run). It checks the superadmin identity of the session (provider and user id) and reads the player row live, in good standing. Pages use `SuperadminGuard`, which reads `getLiveAccess().isSuperadmin`; the league trash page reads no trash data before the viewer is known to be the superadmin.
- **Roles.** Three tiers, in one direction: the superadmin grants and revokes site admin (`is_admin`) and creator (`is_creator`); a site admin edits names and usernames and manages players, but a `PATCH /api/players/[id]` that carries `is_admin` or `is_creator` from anyone else is a 403 (`admin_status_superadmin_only`, `creator_status_superadmin_only`), so a site admin can neither mint, demote nor shield another admin. The superadmin's own player row (the player linked to `SUPERADMIN_DISCORD_ID`, read live) is theirs alone: any `PATCH` of it by anyone else is a 403 `superadmin_player_protected` (a failed read refuses the request), and `/admin/players` offers no Edit control on it to a non-superadmin viewer. The same live, fail-closed check (`superadminPlayerProtectedResponse`, `src/lib/auth/superadmin-player-guard.ts`) refuses a non-superadmin on `POST /api/admin/players/[id]/suspend` (suspend and ban), `POST .../unsuspend` and `DELETE /api/players/[id]` with the same 403, before any write, session-epoch bump or audit row. So do `POST /api/players/[id]/claim` (the superadmin's row as the guest target or as the source, refused before any read, write, audit row or session-epoch bump) and `POST` / `DELETE /api/players/[id]/avatar` when the caller is not the row's owner; `POST /api/admin/players/import` in `upsert` mode skips the superadmin's row per row (`superadmin_player_protected`) for a non-superadmin. The roster hides Suspend, Ban, Reinstate and Delete on that row; a ban would otherwise lock the operator out. A `PATCH` that changes nothing once the schema and the caller's allowance have stripped the body (only `discord_id`, only unknown fields, an empty object) is a 400 `player_update_empty` with no write and no audit event. Identity is not a profile field: `discord_id` and `auth_user_id` are absent from `playerUpdateSchema` and `PlayerUpdate`, `updatePlayer` copies no identity column (`players-update-identity.test.ts` pins it), and an identity moves only through the guarded flows (link, claim, import). There is no admin repair path for a wrong Discord link; the superadmin fixes one in SQL. Every admin `PATCH` that changes `name`, `ps_username`, `champions_username`, `is_admin` or `is_creator` writes one `player.update` audit event listing the changed fields. The superadmin binding itself is described in [A07](#a07--auth-bypass).
- Stored studio definitions (formats, rulesets) are guarded by the live definition row, never the token: `requireRulesetViewer` / `requireRulesetOwner` re-read the player and the definition's metadata (never its draft body), and a malformed or unknown id is a 404 for site admins too. Access rules are pure (`src/lib/studio-core/access.ts`) and tested as an actor-by-definition matrix.
- **A version id is a capability to read that version.** The public ruleset routes serve a version of a *private* ruleset only while a league or phase pins it (a league's page shows its rules to everyone); a guessed or leaked id of an unpinned private version answers 404 (`src/lib/ruleset-studio/exposure.ts`). Usage names (which leagues pin a shared ruleset) are shown only to site admins and the admins of a league-owned ruleset; everyone else gets counts.
- **Owner-rights database functions.** Everything in `public` is `service_role` only. Two league-trash helpers run with the owner's rights (`SECURITY DEFINER`, an empty `search_path`, `EXECUTE` granted to `service_role` only), each for one reason `service_role` cannot do itself: `league_trash_schema_version()` (the highest applied migration, which lives in `supabase_migrations`) and `league_trash__insert_archive_rows(trash_id, step)` (the INSERT of the read-only archive `redraft_trade_requests`, whose INSERT was revoked from `service_role` on purpose; it takes no rows and no SQL from the caller: the rows come from the trash entry and the filter from the restore plan step, and only a step of a table in `league_trash__archive_tables()` is accepted). A new owner-rights function needs the same justification, an empty `search_path` and a test in `src/lib/supabase/__tests__/migration-api-grants.test.ts`.
- **Junction tables make hard deletes fail on purpose.** While a league is in the trash, the foreign keys of `league_trash_players`, `league_trash_rulesets` and `league_trash_point_buy_versions` (`ON DELETE RESTRICT`) make the database refuse a delete of a player, ruleset version or list version the league references (23503). Routes that delete one of these map it with `leagueTrashBlockOf` to a precise message instead of a generic failure.

### A02 — Cryptographic Failures

- All secrets live in environment variables (`.env.local`). Template: `.env.example`.
- Social integration credentials encrypted with `encryptJson()` / `decryptJson()` from `src/lib/social/crypto.ts`.
- Never log secrets, tokens, or API keys — even in a log call.

### A03 — Injection

- **SQL:** All queries use Supabase SDK parameterized methods (`.eq()`, `.in()`, `.ilike()`). Never build raw SQL strings. If raw SQL is needed for migrations, it goes in `supabase/migrations/`.
- **PostgREST logic trees:** `.or()` / `.not()` / `.and()` strings are NOT parameterized: postgrest-js sends them as-is and PostgREST parses `,` `(` `)` `.` in them, so an unquoted user value can add conditions (run by the service-role client). Build them with `src/lib/supabase/postgrest-filter.ts` (`ilikeAnyOf`, `postgrestQuoted`, `escapeLikeTerm`), and pass ids only after `assertValidUuid`. A user LIKE pattern also escapes `%`/`_`/`\` (`escapeLikeTerm`); `*` stays a PostgREST wildcard alias in `like`/`ilike` values.
- **XSS:** React 19 auto-escapes JSX interpolations. Never use `dangerouslySetInnerHTML` with user-controlled content. The single existing usage (`OverlayShell.tsx`) injects static keyframe CSS defined in `src/lib/broadcast/animations.ts`.
- **Command injection:** Never use `eval()`, `Function()`, `child_process.exec()`, or dynamic code execution.

### A04 — Insecure Design

- Rate limits on expensive operations: `src/lib/avatar/rate-limit.ts` (avatar generation), `src/lib/ai/rate-limit.ts` (AI analysis). Both use atomic Supabase RPC with `FOR UPDATE` locks.
- Request rate limits: `src/lib/utils/rate-limit.ts` (`checkRateLimit(bucket, identity, { limit, windowSeconds, failMode })`), one atomic `rate_limit_hit` RPC per check (fixed window in `rate_limit_buckets`, durable across instances and cold starts; identities are stored only as unsalted SHA-256 prefixes, which keeps them out of plain sight but is reversible by brute force for IPv4 addresses, so treat `rate_limit_buckets` (service_role only) as personal data like request logs; `anon` and `authenticated` hold nothing on it, while `service_role` also holds REFERENCES, TRIGGER and TRUNCATE from Supabase's default privileges, which is expected for the server role). The store comes from `RATE_LIMIT_STORE` (validated in `src/lib/env.ts`, documented in `.env.example`): `postgres` uses the RPC; `memory` uses a bounded in-process counter and makes no RPC. Unset means `postgres` only on a Vercel deployment (`VERCEL=1`) and `memory` everywhere else (`next dev`, a local `next start`, the capture harness), so local runs and automation never spend the hosted Supabase quota; NODE_ENV does not decide it. An invalid value never falls back: it stops the server at boot (`src/instrumentation.ts` runs `assertBootEnv()` from `src/lib/env.ts`, which validates `bootEnvSchemas` and throws one `MissingEnvError` naming the key, never the value), so a misconfigured deployment fails once and loudly instead of answering every limited route (signup, forgot-password, password sign-in, calc, proxy-image …) with a 500; the per-call read in `rateLimitStore()` still throws `MissingEnvError` as the backstop. The RPC is raced against a 1.5 s timeout; a timeout counts as a limiter failure. Signed-in routes key on the player id; public routes (for example `/api/proxy-image` 60/min, `/api/replay-frames` 30/min, and the anonymous share-link read `GET /api/teams/shared/[token]` 60/min, checked before the token is validated so well-formed guesses cannot spend unbounded Supabase queries) key on the client IP through `checkPublicRateLimit()` (the LAST `X-Forwarded-For` hop, which the client cannot forge, and for IPv6 only its /64 prefix (`rateLimitIpIdentity`), since one host commonly holds a whole /64; a request with no address header is a local run, which the in-memory store lets through instead of throttling the capture harness in one shared bucket, while the Postgres store still counts it in the shared `unknown` bucket with a warning); the auth routes (`src/lib/auth/rate-limits.ts`) key on the client IP (the same /64 rule) and the inbox the address delivers to (`emailIdentity`: lower-cased, a `+tag` suffix dropped (kept when the local part is only the tag), and for Gmail the dots dropped and `googlemail.com` folded in); `POST /api/account/link-email` counts every attempt per player (5/hour, before the body is read) and every attempt with a valid address per inbox (3/hour), both fail closed; a request with no client IP header skips the per-IP check when a per-email check applies, instead of sharing one site-wide bucket; password sign-in, reset-password and confirm-email have no per-email check, so such a request shares the one `unknown` IP bucket (deliberate: the production host always sets the header, and skipping would switch the brute-force brake off for exactly the requests of unknown origin). Limiter failures are logged and fail open, except signup, forgot-password and resend-verification, which fail closed with a 503 (`rate_limit_unavailable`) because they send email to arbitrary addresses, and `POST /api/bootstrap` and the bootstrap-secret path of `POST /api/seed-rulesets` (one shared `bootstrap` bucket), which fail closed because an uncapped guess at a one-time admin promotion is worse than the route being briefly unavailable. Never set `RATE_LIMIT_STORE=memory` on a deployment: the counter is per serverless instance and resets on every cold start. Auth limits (`AUTH_RATE_LIMITS`): signup, forgot-password and resend-verification 10/hour per IP and 3/hour per email (fail closed); reset-password and confirm-email 10 per 15 min per IP; password sign-in 30 per 15 min per IP (no per-email bucket, so nobody can lock an account owner out).
- Match state transitions enforce a legal state graph — no arbitrary status overwrites.
- Bootstrap (`POST /api/bootstrap`) promotes the caller's existing player row only while no admin exists, atomically (`bootstrap_first_admin` under an advisory lock); it compares the secret with `secretsEqual` (constant time, length-independent), answers "admin exists" before checking the secret once bootstrap is over, and caps attempts per IP with the request limiter (5 per 15 min, shared with the bootstrap-secret path of `POST /api/seed-rulesets`; the cap fails closed with 503 `rate_limit_unavailable`). A rejected secret is logged as a `console.warn` line that never contains the submitted or the expected value. No fixed delays: they are no brute-force control.

### A05 — Security Misconfiguration

- `next.config.mjs` sets security headers: HSTS (2yr + preload), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Permissions-Policy (camera/mic/geo disabled), CSP, COOP: same-origin.
- **CSP, two policies** (`src/lib/security/csp-policy.mjs`, issue #37). The static policy is the enforced default (it keeps `script-src 'unsafe-inline'`, because a static page cannot carry a nonce). `next.config.mjs` sends it on the paths the proxy skips (`PROXY_SKIPPED_SOURCES`, the complement of the proxy matcher: API, `_next/static`, images, the `public/` folders, the service worker files) and sends **no** `Content-Security-Policy` on a page; the proxy sends it on pages, as `buildStaticPolicy({ nonce })`. `src/proxy.ts` makes a fresh nonce per page request, hands it to the render (request headers `x-nonce` and `content-security-policy`; Next stamps its own scripts, the root layout stamps the palette pre-paint script and the theme script) and sends the nonce policy (`script-src 'self' 'nonce-…' 'strict-dynamic' 'wasm-unsafe-eval'` plus the Vercel Analytics script host, no `'unsafe-inline'`, no `blob:`) as `Content-Security-Policy-Report-Only` (without `upgrade-insecure-requests`, which a browser rejects with a console error in a report-only policy; the static policy enforces it, and the enforced nonce policy carries it). Both carry `report-uri /api/csp-report` and `report-to csp` (`Reporting-Endpoints`). With `CSP_ENFORCE` set (`.env.example`), the proxy sends the nonce policy as `Content-Security-Policy` instead of the report-only header, so exactly one enforced policy is sent. **Why the enforced header carries the nonce too, and why pages get no policy from `next.config.mjs`:** Next.js parses the nonce for its own scripts (the `_next/static` chunk tags, the inline `self.__next_f.push` and `$RC`/`$RS` scripts) from the request's `Content-Security-Policy` header, and from the report-only one only when that header is absent (`parseRequestHeaders`, `getScriptNonceFromHeader`: the first `script-src*` directive that holds a `'nonce-…'`). `next start` copies the proxy's response headers onto the request, and Vercel hands the render the response headers of both the proxy and `next.config.mjs` as request headers and lets a `next.config.mjs` `Content-Security-Policy` replace the proxy's request override. With the static policy from the config, the render got a header with no nonce, so on Vercel none of Next's scripts carried one (20 to 100 report-only violations per page; the layout's own scripts read `x-nonce` and were fine), and enforcing would have blocked hydration. Hence: no config policy on pages; in report-only mode the enforced static policy the proxy sends is written `default-src 'self' 'nonce-…'; Script-Src 'self' 'unsafe-inline' …`: a browser reads directive names case-insensitively, so it still applies the same `script-src` with `'unsafe-inline'` and no nonce (a nonce in `script-src` would make it ignore `'unsafe-inline'`, and one in `script-src-attr` blocks inline event handlers, which was measured), while Next.js only recognises a lowercase `script-src`, falls back to `default-src` and finds the nonce there (a nonce-source never matches the kinds of request that fall back to `default-src`); in enforced mode the nonce policy is itself the header. `src/lib/security/__tests__/render-nonce.test.ts` feeds the proxy response and the real `next.config.mjs` headers through Next's own parser and fails when the render finds no nonce. A router prefetch (a request with `next-router-prefetch` or `purpose: prefetch`) still reaches the proxy, but takes a short branch: its response is an RSC payload, not a document, so it gets no nonce, the sign-in and page gates stay off it (a prefetch spends no `pageGate` read and no share-link allowance; the share page counts a prefetch it renders in the separate `team-shared-prefetch` bucket), and the real navigation that follows still gets the redirect, the 404 gate, the nonce and the path header. The branch exists so a client cannot choose the sign-in return path: a request that skipped the proxy (an earlier `missing` condition on the matcher did) handed the page whatever `x-poketools-path` the client sent, and `redirectToSignIn` used it as `callbackUrl`. The branch overwrites `x-poketools-path` and drops `x-nonce`, both CSP request headers and `x-poketools-share-limit`; the matcher is the path pattern alone. A layout never sets a `title` (only the root layout may; `src/app/__tests__/title-template-inheritance.test.ts`), because Next passes a child segment only the title template its parent segment resolved. A page response that does not pass through the proxy gets no CSP; the matcher in `src/proxy.ts` and `PROXY_SKIPPED_SOURCES` must stay complements (`next-config-headers.test.ts` holds them together). Never set `CSP_ENFORCE` on a deployment until a report-only run shows no violations. `POST /api/csp-report` is public, rate limited per IP (60/min, in-process), takes at most 8 KB, answers 204, logs one redacted line per report (query, fragment, token-like path segments, also when percent-encoded, and data/blob payloads removed; at most 600 characters) and stores nothing. Any new inline `<script>` in `src/app` must read the nonce from the `x-nonce` request header (see `src/app/layout.tsx`); the proxy never reads the session. **Vercel preview toolbar:** on a preview deployment (`VERCEL_ENV=preview`, `isVercelPreview()`) Vercel injects `https://vercel.live/_next-live/feedback/feedback.js`; both policies then add `https://vercel.live` to `script-src` and to no other directive (production and local runs never do). **Enforcement decision (#37):** report-only is the default and the production setting; `CSP_ENFORCE` enforces the nonce policy. Enforced mode was proven on a Vercel preview of this change (single enforced nonce header, every script nonced, 0 violations, hydration and client navigation intact, Vercel Analytics loads). Flipping `CSP_ENFORCE` in the production Vercel project is the maintainer's step, taken after a report-only run on production shows no violations; no agent sets it.
- **Sign-in redirects keep the return path** (issue #56). A guard sends an anonymous visitor to `redirectToSignIn()` (`src/lib/auth/redirect-to-sign-in.ts`), which reads the requested path and query from the `x-poketools-path` header the proxy sets and redirects to `/auth/signin?callbackUrl=<path>` through `signInPath()` (`src/lib/auth/safe-callback-url.ts`; only same-origin paths survive, never `/auth*`). A client sign-in link uses `useSignInHref()`. The root `loading.tsx` commits a 200 before a guard's `redirect()` runs, so a signed-out `curl` of a guarded page would get 200 and an in-page redirect; `src/proxy.ts` therefore answers a request with no session cookie at all for `/dashboard`, `/teambuilder`, `/admin`, `/creator/studio` or `/draft-room/trainer-creator` with the 307 to `signInPath(...)` itself (`src/lib/auth/sign-in-gate.ts`). A request that carries any session cookie, valid or not, reaches the guard, which stays the authority. The `(player)` layout gates its view on `requireLiveIdentityOrSignIn()` (same module: `getLiveAccess()`, or the redirect with the return path) and the settings and avatar pages on `requireLivePlayerOrSignIn()` (`getLiveSessionPlayer()`), never on the up-to-5-minute token copy from `getSession()`, so a revoked session ends at sign-in on the next render; the layout lets an authenticated identity with no linked player through, because the dashboard and broadcast pages show their own not-registered guidance to it, so every page under it that acts for a player (dashboard, broadcast hub, match confirm, match prep, the tournament teambuilder) calls `requireLiveIdentityOrSignIn()` first and uses its `player`, never the token's player id. The layout is not re-rendered on a client navigation inside its segment, so those pages (and `AuthGuard`, which reads the same live identity) are the gate that sends a revoked session to sign-in with the exact path and query; only a signed-in identity with no player gets the not-registered guidance (`src/app/(player)/__tests__/live-gates-on-client-navigation.test.tsx`); add a new guarded prefix to `GATED_PREFIXES` only when every page under it requires a session. `src/lib/auth/__tests__/sign-in-redirects.test.ts` fails on a bare `redirect('/login')`, `redirect('/auth/signin')` or a hard-coded `/api/auth/signin` link.
- **Unknown wiki overlay names answer 404 in the proxy.** `/broadcast/wiki/{moves,abilities,items,tera}/<name>` streams with 200 under the root `loading.tsx`, so `isUnknownWikiOverlayName` (`src/lib/broadcast/wiki-overlay-lookup.ts`) answers a 404 before the page, with a minimal transparent HTML document rather than an empty body (Chromium and OBS paint an opaque error page over an empty 4xx body). The id lists are generated from `@pkmn` by `node scripts/generate-wiki-overlay-ids.mjs` (the proxy bundle must not carry the 2 MB dex); `wiki-overlay-ids.test.ts` fails when they drift after a `@pkmn` upgrade.
- **Missing public pages answer a real 404 in the proxy.** The same root `loading.tsx` commits a 200 before a page's `notFound()`, so `pageGate` (`src/lib/seo/page-gate.ts`, called from `src/proxy.ts`) rewrites to the not-found page with status 404 for: a malformed, disabled or unknown `/teams/shared/<token>`, an unpublished or unknown `/teams/library/<id>`, an unknown `/leagues/<id>` or `/tournaments/<id>` (one id-only read each, a hit remembered for a minute in-process, a miss never), and an unknown `/pokemon/<name>` or `/wiki/{moves,abilities,items}/<name>` (the generated id lists above, no database). A share link request spends the common `team-shared` per-IP allowance (60/min, shared with `GET /api/teams/shared/[token]` and the page) exactly once, in the proxy: `pageGate` charges it before the token is looked at (a malformed or missing link answers 404 before the page runs, so only the proxy can count it) and hands the verdict to the page in the `x-poketools-share-limit` request header (`src/lib/seo/share-limit-marker.ts`), which the proxy deletes from every request first, so only a verdict the proxy wrote reaches the page and a client-sent value is ignored. Without a readable verdict the page charges for itself (never skips). Past the allowance the gate reads nothing and the page shows the rate-limited notice, so guessed tokens cannot spend unbounded queries. A species name is a 404 unless its id, or the Mega-, Primal- or Gigantamax- spelling the page's NatDex resolver reads, is in the generated list; a prefix alone is no exemption. A failed read answers `null` and logs: the page decides.
- `poweredByHeader: false` — no X-Powered-By header exposed.
- API routes get `X-Robots-Tag: noindex, nofollow`. Pages behind a login, a bearer token or a viewerless overlay carry `<meta name="robots" content="noindex, nofollow">` (`NOINDEX` in `src/lib/seo/robots.ts`, set by the `(player)`, `(broadcast)`, `auth`, `admin` and `creator` layouts and on `/teams/shared/[token]`) and are listed in `src/app/robots.ts` (`ROBOTS_DISALLOW`); `robots.txt` alone does not stop indexing of a page linked from elsewhere.
- Image sources allowlisted via `images.remotePatterns`.
- **API roles hold no privileges in `public`.** The anon key ships in the browser bundle, so anything `anon` or `authenticated` can read through PostgREST (`/rest/v1/*`) or pg_graphql is public, whatever the app renders. Anyone can sign up, so `authenticated` is no more trusted than `anon`. An RLS policy filters rows, not columns: `USING (true)` exposes every column the role is granted. Neither role holds any privilege on a table, sequence or function in `public`, and postgres's default privileges give new objects nothing for them either (`supabase/migrations/20261008081443_close_public_api_roles.sql`; `public.matches` first in `20261008081402_revoke_anon_private_match_columns.sql`). The exception is an object created outside a migration as `supabase_admin` (the dashboard): that role's default privileges still grant both API roles and postgres cannot change them, so check V7 and V10 after creating one and revoke in a migration. A new migration never grants to `anon`, `authenticated` or `PUBLIC`, and enables RLS on every table it creates; the service-role client is the only reader. To hide some columns but keep others readable, revoke the table privilege and grant a column list: revoking single columns under a table-level grant does nothing. A dump restore does not carry the revokes, so re-run both files after it. The Security Advisor does not catch this (lint 0024 skips `SELECT` policies); verify with `has_column_privilege` and the default-privilege query (`docs/security/anon-match-columns.md`, V1 and V7). `src/lib/supabase/__tests__/migration-api-grants.test.ts` replays the migrations in CI; `src/lib/supabase/__tests__/api-role-grants.local.test.ts` (opt-in, local stack) probes REST as both roles.

### A06 — Vulnerable Components

- Pin major versions in `package.json`. Check changelogs before updating `next-auth` (v5 beta).
- CI runs `npm audit` twice (`.github/workflows/ci.yml`). `npm audit --omit=dev --audit-level=high` blocks on critical/high findings in production dependencies, which is what ships. A second run over all dependencies only reports (`continue-on-error`, since 2026-10-06): dev-tooling findings with no patched release (braces, GHSA-vfj7-8cjw-p6xm) do not block. Fix a dev-only critical/high when a patch exists; never let one reach a production dependency.

### A07 — Auth Bypass

- Session management: NextAuth v5 with JWT strategy. Two providers resolve to the same `players` row: Discord OAuth (`checks: ['state']`) and a Credentials provider backed by Supabase Auth email/password (server-side GoTrue via `src/lib/supabase/auth-client.ts`; no `@supabase/ssr`, no persisted Supabase sessions). See `docs/auth-email-password.md`.
- Superadmin: Discord ID in `SUPERADMIN_DISCORD_ID` (Discord sessions), auto-promoted on every request. An email session is the superadmin only when its email is the optional `SUPERADMIN_EMAIL` AND its player row carries `discord_id === SUPERADMIN_DISCORD_ID` (`src/lib/auth/superadmin.ts`; the email alone is never enough). GoTrue is directly reachable with the public anon key, so anyone can create an auth user on the reserved address; the Discord binding is the control, and with `SUPERADMIN_DISCORD_ID` unset no email superadmin exists. The token and session carry only the derived `superadminLinked` boolean, never the id.
- Session lifetime and revocation: the JWT session lasts 14 days (idle; the cookie slides). Each token carries `authAt`, the sign-in time, stamped at sign-in only (never `iat`, never advanced by a refresh), and `players.sessions_valid_after` is the account-level epoch: a token with `authAt` before it is dead. A password reset, a ban or suspension, a guest claim and "Sign out everywhere" (`POST /api/account/sessions/revoke`) move the epoch forward; lifting a suspension does not. The `jwt` callback returns `null` for a revoked token (the session ends) and every `require*` guard answers **401 `unauthenticated`** (never 403), so an old token cannot outlive a credential change. A token without `authAt` is valid until the first bump. Details: `docs/auth.md`.
- No direct session manipulation — always go through NextAuth helpers.

### A10 — Logging & Monitoring

- Use `safeErrorResponse()` for all API route error handling — it logs the real error server-side and returns a safe fallback message.
- Never expose stack traces, SQL errors, or internal paths in API responses.
- Every error branch that returns a response WITHOUT `safeErrorResponse()` must log the original error first (`logger.error`, `src/lib/logger.ts`). An early-return error branch that logs nothing makes the failure undiagnosable — that is a bug, not a style choice.
- Distinct failure causes must stay distinguishable — via specific safe messages or per-cause `code` values — in both the response and the server logs.
- AI analysis endpoints log token usage via Braintrust (optional).

## Error Handling Pattern (Mandatory)

Every API route catch block must use `safeErrorResponse()`:

```typescript
import { safeErrorResponse } from '@/lib/api/error-response';

export async function POST(request: Request) {
  try {
    const player = await requirePlayer();
    // ... business logic
    return NextResponse.json({ success: true, data: result });
  } catch (err) {
    return safeErrorResponse(err, 'Failed to create resource');
  }
}
```

This helper: (1) passes `UserFacingError` subclasses through — specific message + optional `code` + status, logged server-side, (2) passes `AuthError` messages through (they're user-facing by design) and logs one `logger.warn` line with the `requestId`, status and code, no stack, (3) logs everything else server-side through `logger.error` (tag `api`, with a `requestId` that it also sets as the `x-request-id` response header) and returns the static fallback string to the client.

**Error transparency (mandatory):** generalization, suppression, and masking of errors are forbidden — we need to know what's wrong.

- **No generalization** — never collapse distinct failure causes into one generic message. If four different failures can reach a branch, the client and the server log must both be able to tell which one happened: pass the specific message through when it is safe, or give each cause its own `code`. One shared `code` for all causes disambiguates nothing.
- **No suppression** — never swallow an error. Empty catch blocks, catches that return without logging, and early-return error branches that skip both `safeErrorResponse()` and `logger.error` are bugs. A branch that returns its own `NextResponse` instead of calling `safeErrorResponse()` must `logger.error('<tag>', '<message>', { error: err })` first.
- **No masking** — domain error classes whose messages are constructed to be user-facing (no internals: `AuthError`, and domain errors like the core-assignment errors built from pool/participant counts) keep their specific messages end-to-end. Do not overwrite them with hand-written generic strings in individual routes. The mechanism: extend `UserFacingError` from `src/lib/api/user-facing-error.ts` (carries the safe message + optional `code` + status; `safeErrorResponse()` passes it through and logs it server-side) rather than hand-patching each route. Example: the core-assignment errors in `src/lib/season/core-assignment.ts`.
- The static-fallback rule protects against leaking *internals* (stack traces, SQL errors, unexpected exceptions). It is not a license to hide *domain* errors. When in doubt: log the real error server-side, and return the most specific message that contains no internals.

## Input Validation Pattern

Request-body schemas are Zod, in `src/lib/validation/schemas.ts` ([`validation.md`](./validation.md)); routes without one validate by hand and domain-specifically (see the date-encoding rule in [`src/lib/AGENTS.md`](../src/lib/AGENTS.md)). Follow these patterns:

1. **Whitelist enums** — define `VALID_*` constants, check with `.includes()`:
   ```typescript
   const VALID_CATEGORIES = ['battle', 'draft', 'social'] as const;
   if (!VALID_CATEGORIES.includes(body.category)) {
     return NextResponse.json({ success: false, error: 'Invalid category' }, { status: 400 });
   }
   ```

2. **Length/bounds** — validate string lengths and numeric ranges before processing.

3. **Type guards** — use `parseCreateBody()` style helpers for complex payloads (see `src/app/api/admin/achievements/route.ts` for the pattern).

4. **URL validation** — regex patterns for external URLs (see Discord webhook URL validation in `src/app/api/discord-webhooks/route.ts`).

5. **File uploads** — `validateUpload()` for MIME type and size checks (see `src/app/api/avatar/transform/route.ts`).

6. **UUID path segments** — a dynamic segment that must be a UUID is checked before any query: `const invalid = rejectInvalidPathId(id, 'INVALID_SEASON_ID'); if (invalid) return invalid;` (`src/lib/api/invalid-path-id.ts`). A malformed id names no row, so the answer is **404** with the resource's catalogued `INVALID_<NOUN>_ID` code; without the guard Postgres rejects the non-UUID filter and the route answers 500. Every API route with a UUID path segment carries it, in every handler (GET and the write methods), except the exclusions named in the header of `src/app/api/__tests__/path-id-guards.test.ts`: segments that are not UUIDs (`[name]`, `[species]`, `[pokemon]`, `[token]`, `[...nextauth]`), handlers that read no id (`drafts/[id]/favorites` GET/PUT, and the retired `seasons/[id]/draft-tokens` POST, `seasons/[id]/kill-tokens` GET/POST and `seasons/[id]/redraft` POST, which answer 410 whatever the id), a UUID that arrives as a query parameter (`drafts/route.ts`, guarded in its own test) and any route that header still lists as not yet swept. The shared guard tests pin the `INVALID_*_ID` guards: every guarded public GET is listed in `src/app/api/__tests__/public-path-id-guards.test.ts`, and every guarded handler behind an auth guard in `src/app/api/__tests__/path-id-guards.test.ts`, the league groups (`seasons/[id]/groups/**`) and phase groups (`seasons/[id]/phases/[phaseId]/groups/**`) routes included; a new route adds itself to one of them. Draft routes keep their own convention: their own uuid check, `requireDraftAdmin` or `getQueuePool` answer a malformed pool id with `POOL_NOT_FOUND` (404) before any query, and every such handler is pinned in the shared test (`drafts/[id]` GET/PATCH/DELETE, `state`, `my-turn`, `audit`, `config`, `end`, `extensions`, `free-order`, `pause`, `start`, `picks` GET/POST, `redraft`, `redraft/publish`, `redraft/submission` GET/PUT, `redraft/submissions`, `undo`, `replay-events` POST; the public `replay-events` GET is in the public guard test). A draft route's other segments (`pickId`, `playerId`, `redraftSlotId`) use the `INVALID_*_ID` guard and are in the shared test. The guard runs after the identity guard (`requirePlayer` / `requireAdmin` …), before any query and, where the handler allows it, before the body is parsed; every draft route does (a malformed pool id with a malformed body answers 404). `requireResourceAdmin(type, id)` refuses a malformed season or tournament id itself with the same 404 (`INVALID_SEASON_ID` / `INVALID_TOURNAMENT_ID`, site admins included). A UUID **query** parameter that is malformed is a 400 `INVALID_PARAM` with `params.name`, with one exception: `GET /api/drafts?season_id=` treats the season id like a path segment and answers 404 `INVALID_SEASON_ID` before the identity guard (the answer is the same for everyone, so it reveals nothing; pinned in `path-id-guards.test.ts`).
