## Summary

The posture is better than the architecture implies: every route in this set re-derives identity from the live session and most public endpoints already call the shared limiter, so no critical cross-tenant read or role escalation survived review. The one genuinely exploitable issue is competitive integrity: /api/parse-replay records any public Showdown battle between the two match participants as a game of that match, with no format, date, tournament or global replay-uniqueness binding, and the 24h auto-confirm turns a fabricated win into ratings, standings and bracket movement. Second tier is availability and broadcast integrity on the anonymous overlay surface, where the recap endpoint fans out ~40-50 uncached Postgres queries per request and does not verify that the season, tournament and round ids it was handed belong to each other. The rest are low-severity hardening items: a bearer-style Discord link-intent cookie that is not bound to the requesting session, two public read routes missing the limiter, an unbounded upstream fetch, a fail-open limiter on bootstrap, and a length-leaking secret compare. Fix the replay binding first; it is the only finding a free account can turn into a changed tournament result.

### F1 [P1] Replay submission is not bound to the match: any past battle between the two participants counts as a game

integrity · CWE-345 · confidence medium · `src/app/api/parse-replay/route.ts:32-127`, `src/lib/pkmn/game-pipeline.ts:80-109,163-173`, `src/lib/pkmn/replay.ts:29-52`

- **description:** POST /api/parse-replay fetches any public Showdown replay (route.ts:33) and derives both PS usernames and the winner from the replay log itself (route.ts:34, 89). The only relationship asserted between the replay and the match is that each resolved username maps to match.player_1_id or match.player_2_id (route.ts:72-83). replay.format, the battle timestamp, the tournament/ruleset and the round are never compared, and recordGameResult re-checks only participant identity and match status (game-pipeline.ts:163-173). Duplicate protection loops over match.games only (game-pipeline.ts:100-109) and the schema deliberately leaves games.replay_url without a unique index (supabase/migrations/20261018130000_match_finalize_integrity.sql:12-15), so the same winning replay is reusable in a different match or a later round.
- **path:** authenticated participant -> POST /api/parse-replay { match_id, replay_url } -> fetchReplay(any public battle id) -> winner taken from the replay's |win| line -> recordGameResult with no format/date/uniqueness check -> games row + win count + pending_confirmation
- **impact:** A participant can bank a win in a scheduled or in-progress match using a friendly, a ladder game, an older tournament game, or a replay already used elsewhere. Because the winner id comes from the replay, reaching the Bo threshold moves the match to pending_confirmation with auto_confirm_at = now+24h (game-pipeline.ts:80-88); if the opponent does not actively dispute in that window, finalizeMatchCompletion propagates the fabricated result into aggregates, ratings, standings and the bracket. This is direct competitive-integrity manipulation with only a free account and one real replay where the caller beat the opponent.
- **remediation:** Before calling recordGameResult, require that the replay belongs to this match: compare replay.format against the tournament/round format mapping and reject a mismatch; optionally reject battles older than the match's scheduled_at or the round deadline. Store a normalized replay id on the game and enforce global uniqueness with a unique index (not just a scan of match.games). Keep any legitimate out-of-band import on the existing admin path.
- **verification:** confirmed — Every decisive step checks out: POST /api/parse-replay is an ordinary participant route with no role gate, fetchReplay accepts any public Showdown replay id and returns its `format` but the route never reads it, the only replay-to-match binding is the participant identity check at route.ts:72-83, and recordGameResult validates actor/status and a match-scoped duplicate only — no format, timestamp, round or global replay-id comparison exists anywhere. The Bo threshold then sets pending_confirmation with a 24h timer, which the auto-confirm cron finalizes into ratings/bracket effects; the migration explicitly records that games.replay_url has no unique index, so the same replay can be reused in another match. ### F4 [P3] Discord link intent is an unbound bearer cookie (no session binding, no __Host- prefix)

authz-bypass · CWE-1275 · confidence low · `src/app/api/account/link-discord/route.ts:38-48`, `src/lib/utils/crypto.ts:22-43`, `src/auth.ts:188-225`
