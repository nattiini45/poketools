### Pending Discord link intent is not bound to the initiating session and survives sign-out, so a later first-time Discord sign-in in the same browser profile is linked to the previous player's account [medium]
- attack class: WEB-PROTOCOL-AND-AUTH.md#Account linking and identity collision  ·  unit: src%2Fapp%2Fapi%2Faccount%2Flink-discord%2Froute.ts%23POST::src%2Flib%2Futils%2Fcrypto.ts%23link%20intent%20hmac::src%2Fapp%2Fapi%2Faccount::WEB-PROTOCOL-AND-AUTH.md%23Account%20linking%20and%20identity%20collision
- claim: The next person to use the same browser profile who completes a Discord sign-in and has no player row yet (no session of their own, no knowledge of the cookie). -> The new Discord identity is attached to the previous player's row, and the new person's freshly minted JWT resolves (src/auth.ts:231-259 -> getSessionPlayerRowByIdentity('discord', D2)) to that player. They obtain a normal session for the previous player's account: their match/team data, draft seats and picks, capability share links, and any resource-admin or site-admin authority that player holds, until an admin manually repairs the row. The intent is single-use, so this needs the victim's session to end and the next sign-in to happen inside the 10-minute TTL, and it is refused if the next Discord account already owns a player row (src/auth.ts:213-216) — which aborts that user's sign-in entirely.
- hunter evidence: src/app/api/account/link-discord/route.ts:11,38-48 — the intent is purely a minted bearer cookie (httpOnly, sameSite lax, path '/', maxAge 600s) for the caller's playerId; no server-side record, no session id, no OAuth state/flow correlation is stored, and the route has no sign-out or revocation counterpart. src/auth.ts:194-205 — at consumption the callback only reads the cookie and calls verifyLinkToken; it does not call auth()/requirePlayer, does not compare against the browser's current session, and does not require the initiating session to still be live, so an intent minted by player P is honoured for whichever Discord identity completes sign-in next in that browser. src/auth.ts:212-220 — the link is performed for that playerId as soon as the Discord id has no other owner. src/lib/utils/crypto.ts:27-43 — the MAC covers only `payload.exp`, so the token cannot express `provider`, `state`, or session identity; TTL is the only revocation. Repository-wide grep for LINK_DISCORD_COOKIE returns only src/auth.ts and src/app/api/account/link-discord/route.ts (plus tests) — there is no events.signOut handler and no other route that clears the cookie, so signing out leaves the pending intent valid for the rest of its TTL.
- verifier: Every link in the trace holds in current source, and the boundary crossing is complete without needing runtime observation.

1) Mint (src/app/api/account/link-discord/route.ts:21-48): POST requires a live player (requirePlayer, src/lib/auth/helpers.ts:174-177), rejects players that already have discord_id (:31-36), then mints signLinkToken(player.id, now+600s) and stores it as __poketools_link_discord (httpOnly, sameSite lax, path '/', maxAge 600). Nothing is persisted server-side: no intent row, no session id, no nonce, no OAuth state linkage. Confirmed by reading the whole file (57 lines).

2) Token shape (src/lib/utils/crypto.ts:27-31): the MAC is HMAC(secret, `${playerId}.${expiresAtMs}`). verifyLinkToken (:34-42) checks exactly a 3-part split, expiry, and that MAC, and returns the bare playerId. The token therefore cannot express provider, OAuth state, or the session that minted it — TTL is the only revocation. The hunter's claim here is exact.

3) Consumption (src/auth.ts:188-225): signIn returns early for non-Discord providers (:192); otherwise it reads the cookie (:194-196), deletes it (:199), verifies it (:201), reads profile.id (:207-210), and links if the Discord id has no other owner (:213-219). It never calls auth()/requirePlayer, never compares the browser's current session to playerId, and never requires the initiating session to still exist. I read lines 158-337 in full: there is no `events` key at all, so no signOut handler clears the cookie. Grep for LINK_DISCORD_COOKIE across the repo returns only src/auth.ts:23,195,199, the route (src/app/api/account/link-discord/route.ts:3,42) and route.test.ts — no revocation counterpart, and src/ contains no middleware file that could clear or gate it.

4) Result (src/auth.ts:231-258 + src/lib/supabase/queries/players.ts:87-96,133-142,160-171): linkDiscordToPlayer updates players.discord_id for playerId under `.is('discord_id', null)`; the jwt callback then calls resolveSignInPlayer({provider:'discord', id: D2}), and getSessionPlayerRowByIdentity selects the row `.eq('discord_id', D2)`, which is now P's row. So the second person's session is minted with P's playerId and P's isAdmin/isResourceAdmin/status, and because every later refresh re-reads by (discord, D2), it stays P. Guards re-read live by the same identity, so the second person exercises P's authority, not just a stale copy.

5) Controls that might have refuted it, checked: `checks: ['state']` (src/auth.ts:165) protects CSRF only and is unrelated to the link intent; the 409 at route.ts:31-36 covers only a player that already has discord_id (i.e., the initiator is a credentials player); linkDiscordToPlayer's `.is('discord_id', null)` guard prevents re-linking an already-linked row but says nothing about which human is signing in; and the existing-owner check at auth.ts:214-216 blocks only when the incoming Discord id already owns a *different* player row, which by construction is not the case for a first-time Discord user.

The precondition set is real but coincidental rather than attacker-driven: a shared/reused browser profile, an intent minted and never consumed (any cancelled or failed Discord OAuth leaves it live, since only the callback deletes it), and a second person completing Discord sign-in within 10 minutes with an account that has no player row yet. That caps likelihood, not the demonstrated impact — the impact is a full cross-principal session into the previous player's account. No unlink or change-email flow exists (docs/auth-email-password.md:74), so repair needs an admin.
- fix: Enforce the invariant at the last trusted decision point: an intent is honoured only for the authenticated player it was minted for. In the signIn callback (src/auth.ts:194-210), before linking, decode the session credential carried by the callback request (next-auth/jwt getToken with the request's cookies and NEXTAUTH_SECRET, or an equivalent read of the authjs session cookie) and refuse with `/auth/error?error=LinkExpired` unless that token's `player.playerId` (or `token.id` + `token.provider`) equals the verified `playerId` and `token.provider === 'credentials'` — the provider is knowable because link-discord route.ts:31-36 only mints intents for players without discord_id. Keep the delete-first ordering at :199 so the intent is burned regardless. As the complementary half of the same invariant, add `events: { async signOut() { (await cookies()).delete(LINK_DISCORD_COOKIE) } }` so a pending intent cannot outlive the session that minted it. Regression test in src/__tests__/auth.test.ts: mint an intent for player P, clear the session (sign-out), then run signIn for Discord id D2 in the same cookie jar — assert signIn returns the error redirect, `linkDiscordToPlayer` is never called (add that assertion; the current suite mocks it at :57 but never exercises the cross-session case), and P's row keeps discord_id null. Also assert the happy path still links when the credentials session for P is live during the callback.
