# State machine

Explicit state machines (ADR 0004): every status, phase, timestamp or flag combination that moves through states is defined once with `defineMachine` — its states, its legal transitions and who may perform each one. Writers ask the machine before they write (`assertTransition`), guard the UPDATE with the machine's source states (compare-and-set), and the UI derives the actions it offers from `transitionsFrom(state, actor)`, never from its own status lists. The generated reference with a diagram per machine is [State Machines](./state-machines.md) — do not edit it; it is regenerated by `npm run docs:state-machines`.

## File Structure

```
src/lib/state-machine/
├── machine.ts     # defineMachine + assertTransition + transitionsFrom: the machine contract itself
├── registry.ts    # Every explicit state machine in the app, in one list
└── docs.ts        # The whole of docs/state-machines.md, deterministic, compared byte for byte by the docs test
```

## Core Functions/Classes

- **`defineMachine()`** (`machine.ts`) — builds one machine definition: states, transitions, the actor of each transition. A writer calls `assertTransition(from, to, actor)` before writing and guards the UPDATE with `.eq(column, from)` or `.in(column, machine.sourcesOf(to))`, so a refused move returns its catalog code and a row that moved on is never overwritten.
- **`registry.ts`** — the one list every machine is added to in the same change that defines it. The registry test checks each spec's structure; a new state, transition or writer changes the definition and reruns `npm run docs:state-machines` in the same change (the docs test fails on a stale generated doc).
- **`docs.ts`** — renders the generated reference deterministically, so the docs test compares it byte for byte.
